### 3. 통합 시 결정할 사항

#### 결정 1. 통합 방식

| 방식 | 내용 | 적합한 분석 |
|---|---|---|
| A. 이어 붙이기 (union) | 네 로그를 공통 컬럼 기준으로 위아래로 쌓은 **하나의 타임라인 표** | 시간 순서로 사건 흐름 보기 (멘토 권장 방향) |
| B. 묶음 요약 | 사용자, 호스트, 세션 단위로 집계한 표 | 위험 점수, 이상 행위 비교 |
| C. A + B | 타임라인을 먼저 만들고, 그 위에 요약 표를 만든다 | 둘 다 |

- 멘토 피드백: "로그를 단일 키로 억지로 1:1 조인하기보다, 사용자 식별자·호스트·시간을 함께 보고 **시간 순서에 따른 활동을 분석**하라."
- 따라서 **조인(옆으로 붙이기)보다 이어 붙이기(위아래로 쌓기)** 가 기본이다.

#### 결정 2. 공통 컬럼 목록과 `log_source`

- 이어 붙일 공통 컬럼 목록을 하나로 정한다.
- **어느 로그에서 온 행인지 표시하는 `log_source` 컬럼**을 추가한다 (`sshd`, `nginx`, `sysmon`, `audit`). 지금은 파일 이름으로만 구분된다.
- 공통 컬럼 후보: `event_time_utc`, `log_source`, `dvchost`, `src`, `suser`, `duser`, `cat`, `act`, `outcome`, `reason`, `msg`, `rawEvent`, `unmapped`
- 로그별 고유 컬럼(예: Sysmon `CommandLine`, sshd `connection_id`)을 통합 표에 넣을지, 로그별 파일에서 따로 볼지 정한다.

#### 결정 3. 값이 없는 컬럼 채우기

- 공통 컬럼인데 해당 로그에 없는 값은 **빈 칸(NULL)** 으로 채운다.
  - 예: Sysmon `outcome`, nginx `msg`·`suser`, 감사로그 호스트
- 빈 칸은 "값이 없음"이라는 뜻이다. "실패"나 "0"으로 채우지 않는다.

#### 결정 4. 호스트 컬럼 통일

- 현재 sshd는 `dhost`(접속 대상), Sysmon은 `dvchost`(이벤트 발생 장비)라서, "bastion-01에서 일어난 일 모두 보기"를 하려면 두 컬럼을 따로 봐야 한다.
- 제안: 통합 표에는 **`dvchost` = 로그를 남긴 서버**를 공통으로 둔다.

| 로그 | `dvchost` 값 |
|---|---|
| sshd | `bastion-01` (원래 `dhost`. "접속 대상"이라는 의미로 `dhost`도 함께 남김) |
| Sysmon | `Computer` 값 |
| nginx | **비움** (nginx가 4대 서버 모두에서 실행 중이라 알 수 없음. 멘토 확인 대기) |
| 감사로그 | 비움 (서버가 아니라 SaaS 애플리케이션 로그) |

#### 결정 5. Sysmon `src`를 통합 표에 넣을지

- Sysmon `src`는 **연결을 시작한 서버 자신의 IP**다 (web-01 = 10.10.1.30, app-01 = 10.10.1.20, bastion-01 = 10.10.1.10, node-01 = 10.10.1.40).
- 다른 세 로그의 `src`는 **접속자(사용자, 외부) IP**다.
- 통합 표의 `src`에 함께 넣으면 같은 의미로 오해할 수 있다. 멘토가 직접 경고한 부분이다: "`SourceIp`를 원격 접속자의 IP로 해석하거나 SSHD 등의 접속 IP와 사용자 기준으로 조인하는 데 사용하면 안 된다."
- 선택지:

| 선택지 | 내용 |
|---|---|
| a. 넣지 않음 | 통합 표에서 Sysmon의 `src`는 비우고, Sysmon 파일에서 따로 본다. |
| b. 이름을 바꿔 넣음 | 통합 표에서 `dvc`(deviceAddress, 장비 주소) 같은 별도 컬럼에 넣는다. |
| c. 그대로 넣음 | 반드시 `log_source`와 함께 해석한다는 규칙을 둔다. (오해 위험이 가장 큼) |

- 제안: **b**. CEF `dvc`는 "이벤트가 가리키는 장비의 주소"라서 의미가 맞고, 정보도 잃지 않는다.
- Sysmon의 `dst`, `dpt`(목적지 IP·포트)는 네트워크 흐름 분석에 필요하므로 그대로 넣는다.

#### 결정 6. 사용자 컬럼 해석 규칙

**이름이 같아도 같은 계정이 아니다.** 통합 표에서 사용자 이름으로 그룹을 묶거나 조인하지 않는다.

| 로그 | 컬럼 | 계정 종류 | 예시 |
|---|---|---|---|
| sshd | `duser` | 리눅스 계정 (bastion-01) | `dev01` |
| Sysmon | `suser` | 리눅스 계정 (각 서버) | `dev01`, `root`, `syslog` |
| 감사로그 | `suser` | 테이렌 콘솔 사이트 계정 | `dev01@lab.internal` |

- 멘토 피드백: "`tc_suser`를 SSHD의 리눅스 `user`와 동일 계정으로 간주해 연결하면 안 된다."
- Sysmon `suser`와 감사로그 `suser`는 **CEF 이름까지 같지만 다른 계정**이다.
- **같은 이름 ≠ 같은 계정의 사례:** 감사로그 `ROOT_LOGIN_NO_MFA`의 root는 **테이렌 콘솔의 root 계정**이다 (23건 모두 admin01). 리눅스 root와 다르다.
- sshd `duser`와 Sysmon `suser`는 둘 다 리눅스 계정이다. **같은 서버에서 시각 순서로 비교해도 되는지는 멘토 확인 대기**다.
- 필요하면 통합 표에 계정 종류를 나타내는 컬럼(예: `user_type` = `linux` / `teiren_console`)을 추가하는 방안을 검토한다.

#### 결정 7. 시각 정밀도 차이

| 로그 | 원본 정밀도 | `event_time_utc` 표기 |
|---|---|---|
| sshd | 마이크로초 | `.473850` |
| 감사로그 | 밀리초 | `.256000` |
| Sysmon | 밀리초 | `.000000` 등 |
| nginx | **초** | 항상 `.000000` |

- 모두 6자리로 맞췄기 때문에, nginx의 `.000000`이 실제보다 정밀해 보인다.
- 예: 디버그 실행이 감사로그는 `05:08:14.960`, nginx는 `05:08:14.000`이라 nginx가 먼저인 것처럼 보이지만, 실제 순서는 알 수 없다.
- 규칙: **1초 안의 순서는 판단하지 않는다.** 정렬할 때 같은 초 안에서는 `log_source` 순서 같은 고정 규칙을 둔다.
- 필요하면 통합 표에 `time_precision`(`us` / `ms` / `s`) 컬럼을 둔다.

#### 결정 8. 컬럼 이름 보완 (선택)

| 로그 | 현재 | 대안 | 이유 |
|---|---|---|---|
| sshd | `dproc`, `dpid` | `deviceProcessName`, `dvcpid` | CEF에서 "이벤트를 만든 장비의 프로세스"를 뜻하는 필드가 따로 있다. sshd의 `program`/`pid`는 로그를 쓴 프로세스라 이쪽이 더 정확하다. |

#### 결정 9. 같은 사건이 여러 로그에 남는 경우

- 같은 사건이 두 로그에 동시에 남는다. 예: 디버그 실행 시도가 감사로그와 nginx에 모두 기록된다.
- 이어 붙이면 **같은 사건이 두 행**이 된다. 건수를 셀 때는 `log_source`를 기준으로 하나만 세야 한다.
- 이 경우 결과 표시도 비대칭이다.
  - 감사로그: `GENERAL_BAD_REQUEST` 8건이 `outcome = failure`
  - nginx: 같은 요청이 404인데 `outcome`이 비어 있음 (멘토 피드백으로 status를 쓰지 않음. status는 `unmapped`에 있음)

### 4. 해석할 때 주의할 점

| 로그 | 내용 |
|---|---|
| sshd | logind 450줄의 `connection_id`는 "같은 사용자의 1초 안 직전 로그인"이라는 **시각 기반 추정 연결**이다. 이번 데이터에서는 모두 하나로만 맞았지만, 같은 사용자가 동시에 로그인하면 틀릴 수 있다. |
| sshd | 로그인 횟수는 `cat = authentication`인 줄만 센다. 로그인 한 번에 줄이 8개 나온다. |
| sshd | `Invalid user root`가 40건 있다. 실제 리눅스에는 root가 반드시 있어서 OpenSSH가 보통 남기지 않는 문장이다 (시뮬레이션 흔적). |
| sshd | 외부 IP `203.0.113.44`에서 dev02가 로그인할 때 **평소와 같은 키**를 썼다. "평소와 다른 키" 탐지로는 잡히지 않는다. |
| nginx | 304 응답 186건 모두 본문 크기가 0보다 크다. 원래 304는 본문이 없다 (시뮬레이션 흔적). 응답 크기를 분석할 때 304를 제외할지 정한다. |
| nginx | User-Agent가 1종뿐이라 사용자나 도구를 구분하는 데 쓸 수 없다. |
| Sysmon | web-01의 nginx(`/usr/local/nginx/sbin/nginx`)만 `syslog` 계정으로 실행되고, 나머지 3대의 nginx(`/usr/sbin/nginx`)는 `root`다. web-01이 다르게 구성된 서버라는 분석 단서다. |
| Sysmon | 네트워크·파일 이벤트(EventID 3, 11)의 `ProcessGuid`는 프로세스 생성 이벤트(EventID 1)와 이어지지 않는다. |
| 감사로그 | `outcome`의 `S` = 성공, `G` = 실패는 **추정**이다. |
| 감사로그 | `DEBUG_EXEC`(원격 명령 실행)가 `api / access`로 분류되어 있어 일반 API 호출과 섞일 수 있다. 분류 보완을 검토한다. |
| 감사로그 | `rawEvent`는 한 줄로 압축한 JSON이라 원본과 **내용은 같지만 글자는 다르다.** 대조할 때는 JSON 값으로 비교한다. |
| 감사로그 | `tenancy`(고객사 식별값)가 `unmapped`와 `rawEvent`에 남아 있다. 외부에 공유할 때는 **두 컬럼 모두 마스킹**한다. |

## 보강(Enrichment) 테이블 설명

### 1. 보강이란

로그에 **맥락 정보**를 붙이기 위한 참고 테이블이다. 예를 들어 "이 IP는 누구 PC인가", "이 서버는 무슨 역할인가", "이 행위는 민감한가" 같은 정보다.

- **정규화 데이터는 바꾸지 않는다.** 매핑 테이블만 따로 만들고, 로그에 붙이는 작업은 다음 단계(엔티티 연결·분류)에서 한다.
- 공식 자산 목록이나 인사 정보를 받지 못했기 때문에 **대부분 로그에서 관측하거나 추정한 값**이다. 모든 값에 근거를 표시했다.

### 2. 근거(basis) 표시 규칙

| 값 | 뜻 | 예 |
|---|---|---|
| **공식** | 표준·공식 문서로 정해지는 값 | RFC 1918 사설 대역, Sysmon EventID 정의, OpenSSH·PAM 메시지 의미, HTTP 메서드(RFC 9110) |
| **관측** | 로그 한 행 안에 직접 함께 기록된 값 | Sysmon 한 행에 `Computer=web-01`, `SourceIp=10.10.1.30`이 함께 있음 → web-01의 IP |
| **추정** | 공식 자료가 없어 이름·반복 패턴으로 판단한 값 | 서버 역할, 중요도, 사용자 역할, 감사로그 행위 의미 |

> **추정** 값은 기업(테이렌) 측 확인 전까지 확정하지 않는다. 확인할 항목은 6절에 정리했다.

### 3. 지킨 팀 기준

| 기준 | 출처 | 반영 |
|---|---|---|
| 리눅스 계정(`dev01`)과 테이렌 콘솔 계정(`dev01@lab.internal`)은 다른 계정이다. 이름으로 조인하지 않는다 | 멘토 피드백, [통합 결정 6](04_통합_보강_연결.md#source-1) | `account_system` 컬럼으로 분리. 같은 사람으로 보는 연결은 `person_candidate`에 **추정**으로만 남김 |
| Sysmon `src`는 접속자 IP가 아니라 서버 자신의 IP다 | 멘토 피드백, 통합 결정 5 | 서버 IP 매핑에만 사용. 사용자 연결에는 쓰지 않음 |
| 테이렌 자체 필드(`t_event_id` 등)는 공개 문서가 없다 | [작업정리](README.md) | 감사로그 행위 의미를 전부 **추정**으로 표시 |

### 4. 테이블별 설명

#### 4-1. `ip_inventory.csv`: IP 목록 (21행)

4개 로그에 나오는 모든 IP를 구역별로 나눈다. Sysmon은 접속 대상(`dst`)과 서버 자신(`src`)만 센다.

| 컬럼 | 뜻 |
|---|---|
| `ip_zone` / `zone_basis` | `server` / `user_pc` / `external`과 그 근거 |
| `host` / `host_basis` | 서버 IP이면 서버 이름 (Sysmon 같은 행에서 관측) |
| `is_rfc1918` | RFC 1918 사설 대역 여부 (공식) |
| `is_documentation_range` | RFC 5737 문서용 대역(192.0.2.x, 198.51.100.x, 203.0.113.x) 여부 |
| `linux_login_accounts` | 이 IP에서 sshd 로그인 성공한 리눅스 계정과 횟수 |
| `console_accounts` | 이 IP에서 감사로그에 기록된 콘솔 계정과 건수 |
| `failed_login_accounts` | 이 IP에서 sshd 로그인 실패한 계정명과 횟수 |
| `seen_in_logs` / `event_count` | 이 IP가 나온 로그와 건수 |
| `first_seen` / `last_seen` | 처음·마지막 등장 시각 (UTC) |

구역 판정 결과:

| 구역 | IP | 근거 |
|---|---|---|
| server (4) | 10.10.1.10 / .20 / .30 / .40 | **관측** (Sysmon `Computer`와 `SourceIp`) |
| user_pc (8) | 10.20.10.x | **추정** (사설 대역 + 계정 1개가 반복 접속) |
| external (3) | 45.148.10.151, 165.154.235.9, 213.176.26.69 | **공식** (RFC 1918 밖의 공인 IP) |
| external (6) | 198.51.100.x, 203.0.113.x | **추정** (RFC 5737 문서용 대역. 실제로는 라우팅되지 않으므로 생성 데이터가 외부 IP 대신 쓴 것으로 봄) |

> Python `ipaddress`의 `is_private`는 문서용 대역도 사설로 판정하므로 쓰지 않고, RFC 1918 세 대역을 직접 비교했다.

#### 4-2. `host_inventory.csv`: 서버 목록 (4행)

| host | ip | role (추정) | criticality (추정) | 근거 (`role_evidence`) |
|---|---|---|---|---|
| bastion-01 | 10.10.1.10 | bastion | high | sshd 로그의 유일한 호스트, 외부 SSH 시도가 모이는 관문 |
| app-01 | 10.10.1.20 | application | high | `/opt/app`에서 개발 계정 작업, 소스 코드 보관 |
| node-01 | 10.10.1.40 | operations | medium | 운영 계정(ops01, ops02) 작업 서버 |
| web-01 | 10.10.1.30 | web | high | nginx 실행, `www-data` 활동, 웹 서비스 동작 서버로 추정 |

| 그 외 컬럼 | 뜻 |
|---|---|
| `collected_logs` | 이 서버에서 수집된 로그와 건수. **sshd는 bastion-01만 있다** |
| `interactive_accounts` | 사람 계정이 실행한 프로세스 수 (Sysmon `process_create`) |
| `service_accounts` | root, syslog, www-data 이벤트 수 |

#### 4-3. `account_inventory.csv`: 계정 목록 (23행)

| 컬럼 | 뜻 |
|---|---|
| `account_system` | `linux` (sshd·Sysmon) / `teiren_console` (감사로그) |
| `account_type` / `type_basis` | `human` (추정) / `system` (공식: root, syslog, www-data) / `nonexistent` (관측: sshd가 Invalid user로 기록) |
| `role` / `role_basis` | 계정 이름 접두어로 추정한 역할: developer, operations, administrator, intern, analyst, web_operator |
| `is_privileged` | root, 관리자 계정, 콘솔 root 로그인(`ROOT_LOGIN_NO_MFA`) 계정 |
| `login_success` / `login_fail` | sshd 로그인 성공·실패 횟수 (리눅스 계정) |
| `console_events` | 감사로그 건수 (콘솔 계정) |
| `primary_client_ip` / `other_client_ips` | 가장 많이 쓴 접속 IP / 나머지 IP와 횟수 |
| `active_hosts` / `home_host` | 프로세스를 실행한 서버와 횟수 / 그중 주 작업 서버 (추정) |
| `person_candidate` / `person_basis` | 같은 사람으로 보이는 이름 (**추정**) |

**동일인 후보(`person_candidate`) 판정 방법**

- 이름이 같아서가 아니라, **같은 접속 IP에서 두 계정이 함께 관측됐기 때문**이다.
- 예: 10.20.10.11에서 sshd 로그인 계정은 `dev01`, 감사로그 계정은 `dev01@lab.internal` → 둘 다 `person_candidate = dev01` (추정)
- 이 컬럼은 상관분석 참고용이다. **조인 키로 쓰지 않는다.**

**주 접속 IP 외의 IP(`other_client_ips`)**

- dev02 `203.0.113.44:1`, analyst01@lab.internal `198.51.100.77:10`처럼 평소와 다른 IP를 따로 적었다.
- 이 IP가 정상인지 이상인지는 **여기서 판단하지 않는다.** 다음 단계의 기준선에서 판단한다.

#### 4-4. `action_catalog.csv`: 행위 목록 (30행)

로그별 `event_action`(nginx는 `http_method`)의 의미, 분류, 민감도.

| 컬럼 | 뜻 |
|---|---|
| `vendor_code` | Sysmon EventID, 테이렌 `t_event_id` |
| `category` | authentication, session, process, network, file, view_config, system_config, detection_config, iam_change, admin_exec, error, web_read, web_write |
| `sensitivity` | low / medium / high |
| `meaning_basis` | sshd·Sysmon·nginx는 **공식**, 감사로그는 **추정** |
| `sensitivity_basis` | 모두 **추정** (민감도는 분석자 판단) |
| `sample_request` | 감사로그 행위의 요청 경로 예시 |

민감도 high로 분류한 감사로그 행위 (추정):

| event_action | 이유 |
|---|---|
| `ROOT_LOGIN_NO_MFA` | 최상위 계정이 MFA 없이 로그인 |
| `DEBUG_EXEC` | 내부 디버그 기능으로 명령 실행 |
| `RULE_DELETE` | 탐지 룰 삭제 (방어 체계 변경) |
| `IAM_POLICY_DETACH` | 권한 정책 해제 |
| `IAM_USER_DELETE` | 계정 삭제 |

> 민감도는 특정 사건에 맞추지 않고 **행위의 일반적인 의미**(SIEM에서 탐지 룰 삭제·권한 변경은 민감한 관리 행위)로 정했다.

### 5. 검증 (스크립트 마지막 단계)

- 4개 로그의 모든 IP(sshd·nginx·감사로그 `src`, Sysmon `src`·`dst`)가 `ip_inventory`에 있다.
- 4개 로그의 모든 계정(sshd `duser`, Sysmon `suser`, 감사로그 `suser`)이 `account_inventory`에 있다.
- 서버마다 IP가 하나뿐이다.
- 사용자 PC IP마다 로그인 성공 리눅스 계정이 하나뿐이다. 그래서 동일인 추정이 성립한다.

### 2. 주의할 점

1. **바구니를 시나리오(A~D)에 맞춰 나누지 않는다.**
   - 분류 규칙은 "계정 종류, 로그인 성공 여부"처럼 일반 기준만 쓴다.
   - 그래서 root의 XMR 실행, `www-data`의 셸 실행도 이 단계에서는 **② 시스템 활동으로 분류된다.**
   - 이들을 ① 사용자 세션에 붙이려면 "평소와 다르다"는 판단이 필요하다. 이는 **4~5단계(기준선·탐지)의 일**이다.
   - 따라서 이전 탐색에서 센 숫자(① 4,900 / ② 4,064)와 결과가 조금 다르게 나오는 게 정상이다.
2. **이름으로 조인하지 않는다.** 계정 연결은 같은 로그 안의 키(dpid, 접속 IP+포트, session_id)와 보강 테이블의 IP→계정 매핑으로만 한다. ([통합 결정 6](04_통합_보강_연결.md#source-1), 멘토 피드백)
3. **채운 값과 원래 값을 구분한다.** 원래 컬럼(`src`, `duser` 등)은 그대로 두고, 채운 값은 새 컬럼에 넣고 어떻게 채웠는지 표시한다.

### 3. 세부 작업

#### 2-1. sshd의 빈칸 채우기 (같은 접속 안에서)

sshd는 한 접속이 7~8줄로 나뉘고, 줄마다 IP나 계정이 빠져 있다. 확인 결과 **같은 접속을 묶을 키가 모두 100% 일치**한다.

| 빈칸이 있는 줄 | 묶는 키 | 일치율 | 근거 |
|---|---|---|---|
| `session_opened`, `session_closed` (IP 없음) | `dpid` = `auth_success`의 dpid | 100% | 관측 |
| `disconnect_received` (계정 없음) | `src`+`spt` = `auth_success`의 src+spt | 100% | 관측 |
| `session_logged_out`, `session_removed` (IP·계정 없음) | `session_id` = `session_new`의 session_id | 100% | 관측 |
| `session_new` (IP 없음) | 같은 계정의 `auth_success` 직후 1초 이내 | 공통 키 없음 | **추정** (시간 근접) |

→ 새 컬럼 `connection_id`(로그인 1건 = 1개 ID), `fill_basis`

#### 2-2. 엔티티 컬럼 붙이기

| 새 컬럼 | 값 | 출처 |
|---|---|---|
| `client_ip` | 접속한 쪽 IP (sshd·nginx·감사로그 `src`, sshd는 2-1로 채운 값) | 로그 + 2-1 |
| `client_zone` | user_pc / external | `ip_inventory` |
| `account` | 이벤트의 계정 (sshd·Sysmon 리눅스 계정, 감사로그 콘솔 계정). nginx는 비움 | 로그 + 2-1 |
| `account_system` / `account_type` | linux·teiren_console / human·system·nonexistent | `account_inventory` |
| `person_candidate` | 동일인 후보. nginx는 `client_ip`로 붙임 | `account_inventory`, `ip_inventory` (**추정**) |
| `host` / `host_role` / `host_criticality` | 이벤트가 일어난 서버. sshd는 bastion-01, Sysmon은 `dvchost`, nginx·감사로그는 비움 | `host_inventory` |
| `dst_zone` | Sysmon 네트워크 연결 목적지의 구역 (server / external) | `ip_inventory` |
| `action_category` / `action_sensitivity` | 행위 분류·민감도 | `action_catalog` |

- **Sysmon `process_terminate`(계정 없음 1,458행):** `ProcessGuid`로 같은 프로세스의 `process_create`에서 계정을 가져온다. 근거는 관측이다.
- **nginx·감사로그의 서버:** web-01로 추정되지만 이 단계에서는 붙이지 않고 비워 둔다. 추정을 데이터에 섞지 않기 위해서다.

#### 2-3. 바구니 분류 규칙

| 로그 | 조건 | 바구니 |
|---|---|---|
| sshd | 로그인 성공한 접속에 속한 줄 (`connection_id` 있음) | ① |
| sshd | 실패 줄(`invalid_user`, `auth_failure`) + 그 IP에서 같은 계정 로그인 성공이 **있음** | ① (세션 직전 시도) |
| sshd | 실패 줄 + 그 IP에서 로그인 성공이 **없음** | ③ |
| nginx, 감사로그 | 전부 (사람이 웹으로 접속한 기록) | ① |
| Sysmon | `account_type = human` | ① |
| Sysmon | `account_type = system` (root, syslog, www-data) | ② |

→ 새 컬럼 `bucket`, `bucket_reason` (어떤 규칙으로 분류됐는지)
