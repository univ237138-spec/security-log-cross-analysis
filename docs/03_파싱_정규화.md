**공통 원칙**
- **1단계 파싱만 했다.** 원문의 구조를 나누기만 하고, 값의 의미를 해석하지 않았다.
- **원문을 보존했다.** 값 변환(시각 KST 변환, `-`를 NULL로 바꾸기, 타입 변환)을 하지 않았고, 행 순서도 원본 그대로다.
- **파생 컬럼을 만들지 않았다.** `event_type`, `outcome`, `is_internal_ip` 같은 분류·판단 값은 2단계 정규화에서 만든다.
- **자체 검증을 했다.** 파싱한 값으로 원문을 다시 조립하거나 셀 단위로 대조해서, 빠지거나 바뀐 값이 없음을 확인했다.
- 인코딩은 모두 UTF-8(BOM)이다.

### 1. 검증 이력: 공식 문서를 언제 대조했나

| 시점 | 한 일 | 공식 문서 대조 |

| 파싱 CSV 생성 시 (2026-09-30 오후) | 알고 있던 형식 지식으로 파싱하고, **원문 재조립·셀 대조로 자체 검증** | ❌ 문서를 직접 열어 보지 않음 |
| 이 문서 작성 시 (2026-09-30) | 아래 공식 문서·소스 코드를 직접 열어 파싱 기준과 대조 | ✅ 처음 대조함 |
| 추가 대조 (2026-09-30) | 1차 대조에서 남은 3건(Sysmon EventID 3·5·11 필드, rsyslog 템플릿, systemd 버전별 문장)을 대조 | ✅ 3건 모두 일치 확인 |

### 2. 감사로그 (`audit_parsed.csv`)

#### 파싱 기준
- 원본 컬럼 `EVENT`(Snowflake VARIANT 타입, JSON 객체)의 **키 하나를 컬럼 하나로** 펼쳤다.
- 키 이름과 값은 원본 그대로다. 중첩된 키는 없다.
- 컬럼: 원본 키 15개 + `LOADED_AT` = **16개**

#### 자체 검증
- 456행 모두 JSON 파싱에 성공했다. 모든 행의 키 구성(15개)이 같다.
- CSV를 다시 읽어 원본 JSON 값과 모든 셀을 비교했고, 모두 일치했다.

#### 공식 문서 대조

| 항목 | 기준 문서 | 결과 |
|---|---|---|
| JSON 구조 | JSON 문법 (RFC 8259) | ✅ 표준 JSON이라 해석이 필요 없다. |
| `tc_act` | CEF `act` = deviceAction, "Action taken by the device" | ✅ 의미 일치 |
| `tc_msg` | CEF `msg` = message, 이벤트에 대한 상세 설명 | ✅ 의미 일치 |
| `tc_suser` | CEF `suser` = sourceUserName, "Email addresses are also mapped into the UserName fields" | ✅ 이메일을 넣는 것까지 일치 |
| `tc_src` | CEF `src` = sourceAddress (IPv4) | ✅ 의미 일치 |
| `tc_request` | CEF `request` = requestUrl, "The URL should contain the protocol as well" | △ 의미는 같지만 데이터에는 경로(`/api/...`)만 있고 프로토콜·호스트가 없다. |

### 3. Sysmon (`sysmon_parsed.csv`)

#### 파싱 기준
- `RAW_LINE`의 XML을 **`<System>`과 `<EventData>` 두 부분**으로 나눠 펼쳤다.
- **System:** 태그의 값은 태그 이름으로, 태그의 속성은 `태그_속성` 이름으로 컬럼을 만들었다.
  - 예: `<TimeCreated SystemTime="…"/>`는 `TimeCreated_SystemTime`이 된다.
  - `태그_속성` 이름 규칙은 공식 표준이 아니라 **우리가 정한 규칙**이다.
- **EventData:** `<Data Name="필드명">값</Data>`의 `Name`을 컬럼 이름으로 썼다. EventID마다 필드가 달라서 모든 필드를 합친 형태로 만들었다. 해당 EventID에 없는 필드는 빈 칸이다.
- 컬럼: System 16개 + EventData 37개 + `LOADED_AT` = **54개**

#### 자체 검증
- 5,082행 모두 XML 파싱에 성공했다.
- 원본 XML의 요소 경로는 18종이고, 모두 3단계(`Event → System/EventData → 하위 태그`) 안에 있다. 더 깊은 중첩은 없다.
- 루트 `<Event>`와 `<EventData>`에는 속성이 없다.
- 파싱 코드와 별도로 원본에서 값을 다시 뽑아 **셀 163,894개를 대조**했다. 불일치, 누락, 원본에 없는 값은 모두 0건이다.

#### 공식 문서 대조

| 항목 | 기준 문서 | 결과 |
|---|---|---|
| System 하위 태그와 순서 | Microsoft `SystemPropertiesType` 스키마: Provider(Name, Guid) → EventID → Version → Level → Task → Opcode → Keywords → TimeCreated(SystemTime) → EventRecordID → Correlation → Execution(ProcessID, ThreadID) → Channel → Computer → Security(UserID) | ✅ 데이터의 14개 태그와 순서가 일치 |
| `Correlation`이 빈 태그인 이유 | 스키마상 속성(`ActivityID`, `RelatedActivityID`)이 모두 선택 사항 | ✅ 값이 없는 게 정상이다. |
| `Execution_ProcessID`의 의미 | "Identifies the process that generated the event" | ✅ **Sysmon 자신의 pid**라는 기존 해석이 맞다. 분석 대상 프로세스는 EventData의 `ProcessId`다. |
| `Security` 속성 이름 | 스키마는 `UserID` | △ 데이터는 `UserId`(소문자 d)라서 컬럼 이름을 **데이터 표기**(`Security_UserId`)대로 썼다. |
| 시각 기준 | Sysmon 문서: "Event timestamps are in UTC standard time" | ✅ UTC라는 기존 판단이 맞다. |
| EventID 1, 3, 5, 11의 뜻 | Sysmon 문서: 1 프로세스 생성, 3 네트워크 연결, 5 프로세스 종료, 11 파일 생성 | ✅ 일치 |
| EventID 1 필드 (23개) | OSSEM Linux Sysmon Event ID 1 사전 | ✅ `ParentUser`를 포함한 23개 필드가 모두 일치 |
| EventID 3 필드 (18개) | OSSEM Linux Sysmon Event ID 3 사전 | ✅ `RuleName`부터 `DestinationPortName`까지 18개 필드와 순서가 모두 일치 |
| EventID 5 필드 (6개) | OSSEM Linux Sysmon Event ID 5 사전 | ✅ `RuleName`, `UtcTime`, `ProcessGuid`, `ProcessId`, `Image`, `User` 6개와 순서가 일치 |
| EventID 11 필드 (8개) | OSSEM Linux Sysmon Event ID 11 사전 | ✅ `TargetFilename`, `CreationUtcTime`을 포함한 8개 필드와 순서가 일치 |
| Linux와 Windows의 스키마 관계 | 검색 결과 요약: 두 버전이 같은 manifest와 스키마를 쓴다 | △ 1차 출처(Microsoft 저장소)에서 직접 확인하지는 못했다. |

> 참고: Sysmon 문서에는 EventID 3이 "`ProcessId`와 `ProcessGuid`로 프로세스와 연결된다"고 되어 있다. 하지만 이번 데이터에서는 EventID 3·11의 `ProcessGuid`가 EventID 1과 한 건도 이어지지 않는다. 기록 기간 전부터 실행 중이던 프로세스라서 그런 것으로 보인다.

### 4. nginx (`nginx_parsed.csv`)

#### 파싱 기준
- nginx 기본 로그 포맷 **`combined`의 정의**대로 나눴다. `[ ]`와 `" "` 안의 내용은 하나로 묶었다.
- `request`는 원본 컬럼을 남기고, 공백 기준으로 메서드·URI·프로토콜 3개로 추가 분리했다.
- 컬럼 이름은 **nginx 공식 변수 이름**을 따랐다.
- 컬럼: 포맷 필드 9개 + 요청 분리 3개 + `LOADED_AT` = **13개**

#### 자체 검증
- 2,223행 모두 정규식과 일치했다. 요청 분리도 모두 성공했다.
- 파싱한 값으로 원문을 다시 조립하면 **모든 행이 `RAW_LINE`과 글자 하나까지 같다.**
- 메서드 + URI + 프로토콜을 이어 붙이면 모든 행에서 `request`와 같다.

#### 공식 문서 대조

| 항목 | 기준 문서 | 결과 |
|---|---|---|
| `combined` 포맷 정의 | nginx `ngx_http_log_module`: `'$remote_addr - $remote_user [$time_local] "$request" $status $body_bytes_sent "$http_referer" "$http_user_agent"'` | ✅ 파싱 정규식의 필드 순서·구분 기호와 일치 |
| `ident` 컬럼 | 포맷 정의에서 두 번째 칸은 변수가 아니라 **고정 문자 `-`** | ✅ 데이터도 모두 `-`다. 공식 변수가 아니라서 이름(`ident`)은 관례에 따라 붙였다. |
| `-`의 의미 | "If the variable value is not found, a hyphen (`-`) is logged" | ✅ `remote_user`의 `-`는 값 없음이라는 판단이 맞다. |
| `request` | `$request` = "full original request line" | ✅ |
| `request_method` | `$request_method` = "request method, usually GET or POST" | ✅ |
| `request_uri` | `$request_uri` = "full original request URI (with arguments)" | ✅ 쿼리스트링을 포함한 값이다. 이번 데이터에는 쿼리스트링이 없다. |
| `server_protocol` | `$server_protocol` = "request protocol, usually HTTP/1.0, HTTP/1.1 …" | ✅ |
| `body_bytes_sent` | "number of bytes sent to a client, not counting the response header" | ✅ 본문 크기만 담는다. |
| `time_local` | "local time in the Common Log Format" | ✅ |
| 이스케이프 | 기본 설정에서 `"`, `\`, 제어 문자는 `\xXX`로 기록 | ✅ 데이터에 `\x`가 없어서 따옴표 기준 분리가 깨질 일이 없다. |

### 5. sshd (`sshd_parsed.csv`)

#### 파싱 기준
- **헤더:** `시각 호스트 프로그램[pid]: 메시지`를 정규식 하나로 5개 컬럼으로 나눴다. 메시지 원문은 `message` 컬럼에 그대로 남겼다.
- **메시지:** 문장 구조가 유형마다 달라서, 데이터에 나온 **10개 문장 템플릿**으로 값을 꺼냈다. 원문 전체가 정확히 하나의 템플릿과 일치해야 하고, 맞지 않으면 파싱을 멈추게 했다.
- 꺼낸 값은 **원문에 적힌 글자 그대로**다. 분류 라벨(`event_type`)은 만들지 않았다.
- 컬럼: 헤더 5개 + 메시지 값 13개 + `LOADED_AT` = **19개**

#### 자체 검증
- 1,364행이 모두 템플릿 10개 중 정확히 하나와 일치했다.
- 꺼낸 값을 템플릿에 다시 넣으면 모든 행에서 `message` 원문과 같다.
- 헤더를 다시 조립하면 모든 행에서 `RAW_LINE`과 같다.

#### 공식 문서 대조

| 템플릿 / 항목 | 기준 문서 (소스 코드의 출력 문장) | 결과 |
|---|---|---|
| 헤더 시각 `2026-10-01T03:54:02.473850+09:00` | RFC 3339: `time-secfrac = "." 1*DIGIT`, `time-numoffset = ("+" / "-") time-hour ":" time-minute` | ✅ 마이크로초와 `+09:00` 모두 표준 형식 |
| 헤더 전체 `시각 호스트 프로그램[pid]: 메시지` | rsyslog 예약 템플릿 `RSYSLOG_FileFormat`: `timereported`(rfc3339) + 공백 + `hostname` + 공백 + `syslogtag` + `msg` | ✅ 헤더 구조가 이 템플릿과 같다. `syslogtag`가 `sshd[45208]:`처럼 **프로그램[pid]:** 형태다. 시각이 RFC 3339 형식이라서, 시각이 `Oct  1 03:54:02`인 `RSYSLOG_TraditionalFileFormat`이 아니라 이 템플릿으로 기록된 로그로 판단된다. |
| `Invalid user X from IP port N` | OpenSSH `auth.c`: `"Invalid user %.100s from %.100s port %d"` | ✅ |
| `Accepted/Failed 방식 for X from IP port N ssh2[: 키 정보]` | OpenSSH `auth.c`: `"%s %s%s%s for %s%.100s from %.200s port %d ssh2%s%s"` | ✅ 문장 구조 일치. 키 정보(`: RSA SHA256:…`)가 뒤에 붙는 부분도 형식상 맞다. 키 정보의 세부 표기는 확인하지 못했다. |
| `Received disconnect from IP port N:코드: 사유` | OpenSSH `packet.c`: `"Received disconnect from %s port %d:%u: %.400s"` | ✅ |
| `Disconnected from user X IP port N` | OpenSSH `packet.c`의 `"Disconnected from %s"` + 연결 설명 `"<preamble> <IP> port %d"` + `auth2.c`의 preamble `"user %s"` | ✅ 세 부분을 합치면 데이터 문장과 같다. |
| `pam_unix(sshd:session): session opened for user X(uid=N) by Y(uid=N)` | Linux-PAM `pam_unix_sess.c`: `"session opened for user %s(uid=%s) by %s(uid=%lu)"` | ✅ |
| `pam_unix(sshd:session): session closed for user X` | Linux-PAM `pam_unix_sess.c`: `"session closed for user %s"` | ✅ |
| `Session N logged out. Waiting for processes to exit.` | systemd `logind-session.c`: `"Session %s logged out. Waiting for processes to exit."` | ✅ |
| `Removed session N.` | systemd `logind-session.c`: `"Removed session %s."` | ✅ |
| `New session N of user X.` | systemd `logind-session.c` 버전별 비교: v254·v256·v257은 `"New session %s of user %s."`, v258과 최신 main은 `"New session '%s' of user '%s' with class '%s' and type '%s'."` | ✅ 데이터 문장은 **v257 이하**의 문장과 같다. 수집 서버의 systemd가 v258 이전 버전이라는 뜻이다. 서버를 v258 이상으로 올리면 이 템플릿을 바꿔야 한다. |

> 템플릿 10개는 이번 데이터에 나온 문장만 다룬다. OpenSSH에는 `maximum authentication attempts exceeded …`, `Failed … for invalid user …` 같은 문장도 있지만 이번 데이터에는 나오지 않는다. 새 데이터에 이런 문장이 나오면 파싱이 멈추므로 템플릿을 추가해야 한다.
