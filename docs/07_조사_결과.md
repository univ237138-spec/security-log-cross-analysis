## 7단계 계획: 조사(Investigation) — 경보 검증과 맥락 설계

- 작성일: 2026-10-03
- 상태: 실행 완료 → 사고 카드(로컬 실행 시 생성, 저장소 추적 제외), [02_조사결과_정리.md](07_조사_결과.md#source-2). **질문 목록(7-1)과 판정 기준(7-4)은 실행 전에 이 문서로 고정했고 실행 후 바꾸지 않았다.**
- 앞 단계: [6단계 위험점수](06_탐지_위험점수.md#source-5)
- 참고: [Domain_Knowledge/10_조사_피벗_예시.md](README.md) (시나리오 C를 손으로 따라간 예시)

### 1. 7단계는 어떤 작업인가

6단계에서 경보 4개가 나왔다. 7단계에서는 **이 경보를 받은 분석가 입장이 되어 실제로 의심스러운지 확인하고**, 그 과정에서 **경보에 어떤 정보를 미리 붙여 두면 조사가 빨라지는지**를 정리한다.

이 프로젝트의 7단계는 침해대응 보고서 수준의 깊은 조사가 아니라 **데이터 분석가 관점의 가벼운 조사**다 ([역할 구분](README.md)).

| 하는 것 | 하지 않는 것 |
|---|---|
| 경보 4개가 진짜 의심인지 근거로 확인 (판정) | 공격자 신원·의도 단정 |
| 경보마다 4개 로그를 엮은 사고 타임라인 자동 생성 | 대응 조치 실행 |
| 경보에 붙일 맥락 정보 설계 (조사를 빠르게 하는 정보) | 탐지 룰·점수 수정 (8단계에서) |
| 확인하지 못한 것(데이터 공백) 정리 | |

```
6단계 경보 4개
   │  ① 고정된 질문 목록으로 피벗 (경보마다 같은 순서)
   ▼
사고 카드 4장 (언제·어디서·누가·무엇을·무엇을 남겼나·확인 못 한 것·판정)
   │  ② 조사에 매번 필요했던 정보 정리
   ▼
경보 맥락 설계 (경보에 자동으로 붙일 정보) + 8단계로 넘길 개선 목록
```

| 항목 | 내용 |
|---|---|
| 입력 | `data/10_risk/*`, `data/09_detections/detections.csv`, `data/08_baseline/*`, `data/07_sessions/*`, `data/05_enriched/*` |
| 출력 | `data/11_investigation/` 아래 `incident_timeline.csv`, `pivots.csv`, `triage.csv`, `alert_context.csv` |
| 코드 | `scripts/11_investigate.py` |
| 결과 문서 | `docs/14_조사/01_사고카드.md`(스크립트 생성), `docs/14_조사/02_조사결과_정리.md` |

### 2. 주의할 점

1. **모든 경보에 같은 질문 목록을 같은 순서로 적용한다.** 경보마다 보고 싶은 것만 골라 보면 결론을 미리 정해 놓고 증거를 찾는 셈이 된다.
2. **사실·추정·모름을 구분해 적는다.** 예: 시나리오 A에서 "외부로 업로드했다"는 연결 기록(관측)까지만 확인된다. "유출에 성공했다"는 로그로 알 수 없다.
3. **과장하지 않는다.** 로그로 확인되지 않은 것(공격 성공, 같은 공격자, 의도)은 단정하지 않는다.
4. **조사 결과로 지금 탐지·점수를 고치지 않는다.** 개선점은 목록으로 남겨 8단계로 넘긴다.
5. **경보가 아닌 상위 세션도 확인한다.** 20점 정상 세션 7개가 정말 정상인지도 같은 방식으로 짧게 확인한다.

### 3. 세부 계획

#### 7-1. 고정 질문 목록 (모든 경보에 같은 순서로)

| # | 질문 | 피벗 키 | 사용 데이터 |
|---|---|---|---|
| Q1 | 무엇이 경보를 만들었나? | 세션 | `session_risk`, `risk_events` |
| Q2 | 누구인가? 평소와 같은가? | 사람 후보, 계정 | `session_baseline`, 같은 사람의 과거 세션 |
| Q3 | 어디서 왔나? 그 IP는 다른 곳에도 나오나? | 접속 IP | 전체 타임라인, `ip_inventory` |
| Q4 | 어떻게 들어왔나? | 세션 | sshd 인증 방식·실패, 웹 로그인 종류 |
| Q5 | 무엇을 했나? (시간순) | 세션 + 연결된 시스템 이벤트 | 4개 로그 타임라인 |
| Q6 | 무엇을 남겼나? | 세션 | 생성 파일, 외부 연결, 계정·설정 변경 |
| Q7 | 퍼졌나? | 서버, 외부 IP | 같은 서버의 다른 세션·이벤트, 외부 IP의 다른 등장 |
| Q8 | 확인 못 한 것은? | – | 데이터 공백 목록 |
| Q9 | 판정 | – | 7-4 기준 |

#### 7-2. 사고 타임라인 자동 생성

- 경보 세션마다 세션 시작 30분 전부터 종료 30분 후까지 다음을 시간순으로 모은다.
  - 세션 소속 이벤트
  - 5-c로 연결된 시스템 이벤트
  - 같은 접속 IP와 같은 서버의 이벤트
- 행마다 표시: 로그, 내용 요약, 탐지 ID, **사실/추정 구분**(세션 직접 소속 = 관측, 5-c 연결·시간 근접 = 추정)
- 반복 정상 활동(전체 100회 이상 나온 시스템 패턴)은 접어서 건수만 표시한다.

#### 7-3. 피벗 결과 자동 계산

| 피벗 | 계산 |
|---|---|
| 사람의 평소 | 과거 세션 수, 평소 시작 시각 범위, 평소 IP, 평소 세션 종류, 직전 세션 시각 |
| IP의 다른 등장 | 그 IP가 나온 로그·세션·건수, 처음·마지막 시각 |
| 외부 목적지의 다른 등장 | 외부 IP가 다른 서버·세션에 나온 적 있나 |
| 서버의 같은 시간 | 같은 서버에 같은 시간 접속한 다른 세션 |
| 경보 간 관계 | 경보끼리 공유하는 사람·IP·서버, 시간 간격 |

#### 7-4. 사고 카드와 판정 기준 (실행 전 고정)

판정은 두 가지를 나눠서 본다.

| 축 | 값 | 기준 |
|---|---|---|
| **활동 판정** (이 활동이 의심스러운가) | 의심 확인 | high 룰 신호가 1개 이상이고, 그 신호의 원본 이벤트가 로그에 관측됨 |
| | 오탐 후보 | 룰 신호 없이 행위 탐지만 있고, 그 이탈이 정상 업무 범위로 설명됨 |
| | 보류 | 위 둘 다 아님 |
| **귀속 판정** (이 세션·사람의 활동인가) | 관측 | high 룰 신호 중 세션에 직접 소속된 것이 있음 |
| | 추정 | high 룰 신호가 모두 5-c 추정 연결 |

사고 카드 구성: 요약, Q1~Q8 답, ATT&CK 전술 순서, 판정과 근거, 확인 필요 사항.

#### 7-5. 비경보 상위 세션 확인 (미탐 점검)

- 20점 세션 7개에 Q1~Q3를 적용해 왜 걸렸고 정상으로 볼 근거가 있는지 확인한다.
- 오탐 원인을 기록해 8단계로 넘긴다.

#### 7-6. 경보 맥락 설계 + 8단계 넘길 목록

| 산출 | 내용 |
|---|---|
| 경보 맥락 필드 | 조사에서 매번 직접 찾아야 했던 정보를 경보에 자동으로 붙일 필드로 정리 |
| 데이터 공백 목록 | 조사에서 답할 수 없었던 질문과, 그 답에 필요한 로그 |
| 8단계 개선 목록 | 오탐 원인, 미탐 후보(R09 저속 대입 등), 룰·임계값 개선 아이디어 |

#### 7-7. 검증

- 경보 4개 모두 Q1~Q9 답이 있음
- 타임라인의 탐지 표시가 `detections.csv`와 일치함
- 사고 카드의 모든 항목에 사실/추정/모름 표시가 있음

### 3. 경보 맥락 설계 (데이터 분석가의 핵심 산출물)

조사하면서 **매번 직접 찾아야 했던 정보**를 정리했다. 이 정보를 경보에 자동으로 붙이면 분석가의 조사 시간이 줄어든다. `alert_context.csv`가 실제 값을 채운 예시다.

| 맥락 필드 | 답하는 질문 | 이번 조사에서 쓰인 곳 |
|---|---|---|
| `tactic_chain` | 공격이 어떤 단계로 진행됐나 | 4개 모두 (예: S137 실행 → 명령·제어 → 방어 회피 → 탐색 → 측면 이동) |
| `top_signals` | 무엇이 점수를 올렸나 | Q1 |
| `start_kst`, `usual_hours_kst`, `hour_distance` | 평소 일하는 시간인가 | S137 (평소 8~16시, 이번 2시), S122 (3시) |
| `client_ip`, `ip_zone`, `ip_first_time_for_person` | 평소 쓰는 곳에서 왔나 | S122, S132 (처음 보는 외부 IP) |
| `session_type`, `usual_session_types` | 평소처럼 웹·서버를 함께 썼나 | S122·S137 (웹 없음), S132 (ssh 없음) |
| `hours_since_prev_session` | 직전 활동과 얼마나 떨어졌나 | S137 (14.6시간 전) |
| `failed_before_login`, `web_login` | 어떻게 들어왔나 | S122 (실패 3회 후 성공), S132 (새 기기) |
| `linked_system_activity` | 세션 밖 시스템 활동과 이어지나 (추정 표시) | S132 (web-01), S137 (node-01) |
| `files_created`, `external_destinations` | 무엇을 남겼나 | S122, S132, S137 |
| `external_dest_seen_elsewhere` | 이 외부 목적지를 다른 곳에서도 봤나 | 4개 모두 0건 → 다른 피해 서버 없음 |
| `config_changes` | 계정·설정을 바꿨나 | S142 |
| `concurrent_sessions_same_host` | 같은 서버에 같은 시간 다른 사람이 있었나 | 4개 모두 없음 → 귀속 추정의 다른 후보 없음 |
| `data_gaps` | 확인할 수 없는 게 몇 개인가 | 4개 모두 1~4개 |
| `activity_verdict`, `attribution` | 판정 | 1절 |

**설계 원칙:**
- 모든 필드는 4~6단계 결과에서 자동으로 계산할 수 있다.
- 추정이 들어간 필드(`linked_system_activity`, `attribution`, 사람 후보)는 추정이라는 표시를 함께 붙인다.

### 4. 데이터 공백: 답할 수 없었던 질문과 필요한 로그

| 공백 | 영향받은 경보 | 답하려면 필요한 로그 |
|---|---|---|
| bastion-01에서 담당 서버로 넘어간 ssh 기록 없음 | S122, S137, S142 | app-01·node-01·web-01의 sshd 로그 |
| 시스템 계정(root·www-data) 활동이 누구의 것인지 | S132, S137 | Linux auditd의 `auid`(로그인 사용자 ID, sudo 뒤에도 유지), sudo 로그 |
| 탐지된 프로세스의 부모 프로세스 기록 없음 (권한을 어떻게 얻었나) | S122, S132, S137 | Sysmon 수집 범위 확대 (수집 시작 전부터 떠 있던 프로세스 포함), auditd |
| 웹 요청이 어떻게 서버 명령 실행으로 이어졌나 | S132 | 애플리케이션 로그, nginx와 앱이 공유하는 요청 ID(`$request_id`) |
| 외부 전송의 내용·양·성공 여부 | S122, S132, S137 | 방화벽·프록시 로그(전송 바이트), DNS 로그(`files.transfer-example.net` 조회), NetFlow |

데이터 공백은 분석 실패가 아니라 **수집 개선 과제**다. 기업 측에 "이 로그가 있으면 이 질문에 답할 수 있다"는 형태로 전달할 수 있다.
