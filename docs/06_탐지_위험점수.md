## 5단계 계획: 탐지(Detection)

### 1. 5단계는 어떤 작업인가

4단계에서는 "평소와 얼마나 다른가"를 숫자로만 남겼다. 5단계는 그 숫자와 로그 내용을 보고 **"이건 의심 신호다"라고 표시하는 작업**이다. 실무에서처럼 두 가지 방식을 함께 쓴다.

| | 5-a 룰 기반 탐지 | 5-b 행위 기반 탐지 |
|---|---|---|
| 질문 | **무엇이 확실히 나쁜가?** | **누가 평소와 다른가?** |
| 근거 | 알려진 공격 기법 (MITRE ATT&CK) | 4단계 기준선 비교값 |
| 예 | 웹 서버 계정이 셸을 실행함 | 평소 09~16시에 일하던 사람이 02시에 접속함 |
| 장점 | 정확하고 이유가 명확함 | 처음 보는 공격도 잡을 수 있음 |
| 단점 | 모르는 공격은 못 잡음 | 정상 변동도 잡혀 오탐이 생김 |

```
4단계 비교값 ──▶ 5-b 행위 탐지 ──┐
                                 ├──▶ 탐지 신호 목록 ──▶ 6단계 위험점수
로그 원본 ─────▶ 5-a 룰 탐지 ────┘        (아직 경보 아님)
```

5단계의 결과는 **경보가 아니라 "탐지 신호" 목록**이다. 신호마다 몇 점인지, 몇 점부터 경보인지는 6단계에서 정한다.

5단계에는 하나가 더 있다. 2단계부터 ② 시스템 활동에 남아 있던 **root·www-data의 의심 활동을 사용자 세션에 연결**하는 일이다 (5-c).

| 항목 | 내용 |
|---|---|
| 입력 | `data/07_sessions/timeline_sessions.csv`, `data/08_baseline/*`, `data/05_enriched/*` |
| 출력 | `data/09_detections/detection_rules.csv`, `detections.csv` |
| 코드 | `scripts/09_detect.py` |
| 결과 문서 | `docs/12_탐지/01_탐지_설명.md` |

### 2. 주의할 점

1. **룰은 데이터를 보기 전 기준으로, 일반적인 공격 기법으로 쓴다.** 특정 IP, 파일 이름, 계정은 조건에 넣지 않는다. 예를 들어 `setup_xmr.sh`가 아니라 "인터넷에서 받은 스크립트를 바로 셸로 실행"처럼 쓴다. 룰 목록은 이 문서에 **실행 전에 고정**한다.
2. **행위 탐지 임계값은 분포로 정하고 방법을 미리 정한다.** "이 정도면 이상"을 눈으로 고르지 않고, 미리 정한 방법(드문 정도 기준)으로 계산한다.
3. **오탐을 0으로 만들려고 조정하지 않는다.** 정상 세션이 일부 잡히는 게 자연스럽다. 오탐은 기록해 두고 6단계 점수와 8단계 평가에서 다룬다.
4. **같은 사건을 두 번 세지 않는다.** nginx와 감사로그는 같은 요청을 둘 다 기록한다. 웹 행위 룰은 감사로그 기준으로만 걸고, nginx는 요청 패턴(반복 오류 등)에만 쓴다.
5. **과거가 부족한 세션의 행위 탐지는 걸지 않는다.** 기준선이 `global`·`none`인 세션은 "처음 봄"이 당연하니 행위 탐지에서 제외하고, 제외한 수를 기록한다.

### 3. 세부 계획

#### 5-a. 룰 기반 탐지 (실행 전 고정)

일반 공격 기법을 로그 필드 조건으로 옮긴 룰이다. 공개 탐지 룰 모음(Sigma)에 있는 유형들이다.

> **정정 (2026-10-07, 원문 유지):** 위 문장은 16개 전체에 맞지 않는다. 실행한 뒤에 SigmaHQ 룰과 하나씩 대조한 결과는 다음과 같다. 상세는 [02_Sigma_대조표.md](06_탐지_위험점수.md#source-3)에 있다.
> - Sigma 룰과 조건이 거의 같은 룰: R08 (1개)
> - Sigma 룰을 변형한 룰: R01, R02, R04, R07 (4개)
> - 개념만 대응하는 룰: R05, R06, R12, R13, R16 (5개)

#### 5-b. 행위 기반 탐지 (4단계 비교값 + 임계값)

대상: 기준선이 `person` 또는 `peer`인 세션 (B09는 ② 이벤트).

| ID | 탐지 | 4단계 비교값 | 임계값 결정 방법 |
|---|---|---|---|
| B01 | 평소와 다른 시작 시각 | `hour_distance` | 드문 정도 기준으로 계산 |
| B02 | 처음 보는 접속 IP | `ip_new` | 참이면 |
| B03 | 평소와 다른 접속 경로 | `hist_session_type_ratio` | 0이면 (과거에 한 번도 없던 세션 종류) |
| B04 | 처음 보는 로그인 종류 | `login_types_new` | 값이 있으면 |
| B05 | 처음 하는 민감 행위 | `sensitive_new` | 값이 있으면 |
| B06 | 누구도 쓴 적 없는 명령 | `cmds_new_global` | 값이 있으면 |
| B07 | 로그인 전 실패 첫 발생 | `failed_before_login`, `hist_failed_sessions` | 실패 > 0이고 과거 실패 세션 0 |
| B08 | 평소보다 많은 양 | `{항목}_above_max` | 드문 정도 기준을 통과한 항목만 사용 |
| B09 | 처음 보는 시스템 활동 패턴 | `pattern_seen_before`, `pattern_seen_other_hosts_before`, `host_history_hours` | 같은 서버·다른 서버 모두 처음 보는 패턴 + 서버 기록 24시간 이상 |

**드문 정도 기준 (B01, B08):** 비교 가능한 세션(person·peer) 중 **5% 이하에서만 나오는 값**부터 이상으로 본다.

- B01: `hour_distance ≥ d`인 세션 비율이 5% 이하가 되는 가장 작은 d를 임계값으로 쓴다.
- B08: 항목별로 `_above_max`가 참인 세션 비율이 5% 이하인 항목만 탐지에 쓴다.
- 5%는 통계에서 흔히 쓰는 "드묾"의 기준이다. 실행 시 실제 비율을 출력해 결과 문서에 남긴다.

**B09의 24시간 근거:** healthcheck 중 가장 늦게 처음 나타난 패턴(`rotate.sh`)이 서버 기록 시작 후 약 12~17시간에 나왔다. 하루 주기 작업이 한 번씩은 나타나도록 최소 하루를 학습 기간으로 둔다.

#### 5-c. 시스템 활동 탐지를 사용자 세션에 연결

5-a·5-b에서 ② 시스템 이벤트(root·www-data)에 걸린 탐지를 **그 시간에 그 서버에서 활동 중이던 사용자 세션**에 연결한다.

| 연결 규칙 | 근거 |
|---|---|
| 같은 서버에서 ssh 세션 시간 안에 있던 서버 세션 (세션의 작업 서버 또는 사람의 주 작업 서버가 그 서버) | 그 서버에 접속해 있던 사람 (서버·시간) |
| 웹 서버(`host_role = web`, 추정)의 이벤트라면, 앞뒤 5분 안에 웹 요청을 보낸 세션 | 웹 요청이 서버 실행을 일으킬 수 있음 |

- 후보가 여럿이면 모두 남기고 시간 차이를 기록한다. 연결 근거는 모두 **추정**으로 표시한다.
- 연결 후보가 없으면 "연결 없음"으로 남긴다. 서버에서 저절로 일어났거나 수집되지 않은 경로로 들어온 경우다.

#### 5-d. 산출물

| 파일 | 내용 |
|---|---|
| `detection_rules.csv` | 룰·행위 탐지 정의 (ID, 이름, 조건, ATT&CK, 심각도, 사용 로그, 계산된 임계값) |
| `detections.csv` | 탐지 신호 1건 = 1행: 탐지 ID, 방식(rule/behavior), 대상(세션/서버/IP), 시각, 사람 후보, 근거, 원본 행 번호, 연결된 세션과 연결 근거 |

#### 5-e. 검증과 요약

- 모든 탐지에 대상과 근거가 있음
- 세션 연결이 있는 탐지는 연결 근거가 있음
- 출력: 룰별·행위별 탐지 수, 탐지가 1개 이상인 세션 수, 행위 탐지에서 제외한 세션 수(global·none)
- 시나리오 A~D 세션이 잡혔는지, 정상 세션이 몇 개 잡혔는지 **참고로만** 출력한다. 정식 평가는 8단계에서 한다.

#### 5-f. 문서

`docs/12_탐지/`에 계획(00, 이 문서)과 결과(01). 결과 문서에는 룰의 ATT&CK 근거, 임계값 계산 결과, 오탐 사례, 한계를 적는다.

- 룰은 특정 IP·파일 이름·계정을 조건으로 쓰지 않았다. 예: R02는 "curl/wget 출력을 셸로 파이프", R06은 "임시 폴더의 `.`으로 시작하는 파일", R12~R14는 1단계 행위 분류(`detection_config`, `iam_change`, `admin_exec`) 기준이다.
- 정상 활동(healthcheck, 정상 명령 5종, 내부 서버 간 nginx 통신)에서는 R16 외 룰이 하나도 걸리지 않았다.

### 3. R09가 0건인 이유: 느린 무차별 대입

- 외부 IP 3개는 16일 동안 각각 46~66회 시도했다. 하루 3~4회꼴이라 **1시간 안 5회** 조건을 한 번도 넘지 않았다.
- 이런 방식을 "느린 무차별 대입(low-and-slow)"이라고 부른다. 짧은 시간 창 룰을 피하는 전형적인 방법이다.
- 계획대로 **룰을 바꾸지 않았다.** 이 시도들은 4단계 `external_profile.csv`에 IP별로 요약돼 있다.
- 개선 후보: 24시간이나 7일 창으로 "같은 IP의 서로 다른 계정명 시도 수"를 세는 룰. 다음 튜닝(8단계) 때 검토한다.

### 7. 한계

#### ① 시나리오를 알고 있는 상태에서 룰을 골랐다

- 룰 조건은 일반 기법으로 썼지만, **어떤 일반 기법을 룰 목록에 넣을지**는 시나리오를 아는 상태에서 정했다.
- 예: R06(임시 폴더 숨김 파일), R07(압축), R08(업로드)은 Sigma에 있는 일반 룰 유형이다. 그래도 이 데이터에 그런 행동이 있다는 걸 알고 골랐다.
- 그래서 룰 탐지율이 높게 나오는 건 당연한 면이 있다. 결과는 **탐색적 평가**로 보고한다.
- 반대로 R09처럼 미리 고정한 기준이 데이터와 안 맞아 0건이 나온 경우도 그대로 두었다.

#### ② 임계값 계산에 공격 세션도 포함됐다

- B01·B08의 5% 기준은 비교 가능한 세션 126개 전체(공격 세션 포함)의 분포로 계산했다.
- 공격 세션은 4개뿐이라 영향은 작다. 하지만 엄밀하게는 정상 세션만으로 계산해야 한다. 정상·공격 구분을 모르는 실무 상황을 따른 것이다.

#### ③ 그 외

| 항목 | 내용 |
|---|---|
| 작은 표본 | 비교 세션 126개라 5%는 약 6개 세션이다. 임계값이 몇 세션에 따라 크게 바뀔 수 있다 |
| 5-c 연결 | 모두 추정이다. 이 데이터에서는 후보가 하나씩이었지만, 같은 시간에 여러 명이 접속한 실제 환경에서는 후보가 여럿 나온다 |
| 웹 서버 판단 | web-01이 웹 서버라는 것은 보강 테이블의 추정이다 |
| 탐지 단위 | 룰 탐지는 이벤트 단위다. 한 공격 단계가 여러 이벤트로 남으면 탐지도 여러 건 생긴다 (예: B09가 node-01에서 6건). 6단계에서 중복을 어떻게 셀지 정해야 한다 |
| nginx·감사로그 | R11·R12~R14는 감사로그만, R15는 nginx만 써서 같은 요청을 두 번 세지 않았다 |

#### 이 결과가 말해 주는 것

1. **Sigma 원본만 썼다면 S132의 웹 명령 실행(R01·R02)과 S137의 다운로드 실행·스캔·숨김 파일(R02·R05·R06)을 놓쳤다.** Sigma 원본으로 잡히는 것은 S122의 압축·업로드와 S137의 4444번 연결뿐이다.
2. **그렇다고 우리 룰이 더 좋다는 뜻은 아니다.** 우리 룰은 이 데이터에 그런 행동이 있다는 걸 알고 일반화한 것이다([01_탐지_설명.md](06_탐지_위험점수.md#source-2) 한계 절). 차이의 일부는 우리가 이 데이터에 맞춰서 생긴 것이다.
3. **문자열 일치 룰은 표기에 약하다.** 따옴표 하나, 경로 유무(`curl`과 `/usr/bin/curl`) 때문에 Sigma 룰이 빗나갔다. 같은 일이 우리 룰에도 생길 수 있다. 8단계 변형 주입 실험(명령 표기 바꾸기)에서 확인할 항목이다.

## 6단계 계획: 위험점수(Risk Scoring)

- 작성일: 2026-10-03
- 상태: 실행 완료 → [01_위험점수_설명.md](06_탐지_위험점수.md#source-5). **점수 가중치(6-1)와 경보 기준(6-4)은 실행 전에 이 문서로 고정했고 실행 후 바꾸지 않았다.**
- 앞 단계: [5단계 탐지](06_탐지_위험점수.md#source-2)
- 전체 흐름: [Domain_Knowledge/09_보안로그_분석_워크플로우.md](README.md) 5절

### 1. 6단계는 어떤 작업인가

5단계에서 탐지 신호 76건이 나왔다. 신호를 하나하나 전부 경보로 띄우면 이런 문제가 생긴다.

- admin01은 로그인할 때마다 R16이 떠서 경보가 23번 울린다.
- 정상 세션 7개는 행위 탐지 하나씩만 걸렸는데도 공격 세션과 똑같이 경보가 된다.
- node-01 공격 하나에서 B09가 6건 나와 같은 사건이 6번 울린다.

이것이 실무에서 말하는 **경보 피로(Alert Fatigue)** 다. 6단계는 이를 해결하는 실무 방식인 **위험 기반 경보(RBA, Risk-Based Alerting)** 를 적용한다.

```
5단계: 탐지 신호 76건 (낱개)
         │  ① 신호마다 점수 매기기 (심각도 × 자산 중요도 × 신뢰도)
         │  ② 같은 대상(세션·사람·서버)에 점수 쌓기
         ▼
6단계: 세션 146개의 위험점수 순위표
         │  ③ 점수나 공격 단계 수가 기준을 넘으면 경보
         ▼
       경보 몇 건 (분석가가 볼 목록)
```

핵심은 **"신호 하나로는 경보를 띄우지 않고, 같은 대상에 신호가 쌓였을 때 띄운다"** 이다.

| 항목 | 내용 |
|---|---|
| 입력 | `data/09_detections/detections.csv`, `data/07_sessions/sessions.csv`, `data/05_enriched/host_inventory.csv`, `data/08_baseline/external_profile.csv` |
| 출력 | `data/10_risk/` 아래 `risk_events.csv`, `session_risk.csv`, `entity_risk.csv`, `config_findings.csv`, `sensitivity.csv` |
| 코드 | `scripts/10_risk.py` |
| 결과 문서 | `docs/13_위험점수/01_위험점수_설명.md` |

---

### 2. 주의할 점

1. **점수 가중치는 임의값이라는 걸 인정하고, 실행 전에 고정한다.** "공격 세션이 1등이 되도록" 숫자를 맞추면 안 된다. 가중치를 미리 정하고, 가중치를 바꿔도 순위가 유지되는지 **민감도 확인**으로 보여준다.
2. **같은 신호의 반복으로 점수가 부풀지 않게 한다.** 한 세션에서 같은 종류의 탐지가 여러 번 나와도 한 번만 센다.
3. **점수의 근거를 항목별로 남긴다.** 어떤 신호가 몇 점씩 더해졌는지 같이 남겨 "왜 위험한지" 설명할 수 있게 한다.
4. **행동 위험과 설정 위험을 섞지 않는다.** R16(MFA 없는 root 로그인)은 계정 설정 문제다. 세션 점수에서 빼고 **설정 위험 목록**으로 따로 보고한다.
5. **추정 연결의 신뢰도를 낮춘다.** 5-c에서 시간·서버로 추정 연결한 신호는 세션에 직접 속한 신호보다 점수를 조금 깎는다.

---

### 3. 세부 계획

#### 6-1. 신호 점수 (실행 전 고정)

```
신호 점수 = 기본 점수 × 자산 중요도 계수 × 신뢰도 계수
```

| 요소 | 값 | 근거 |
|---|---|---|
| 기본 점수: 룰 high / medium / low | 60 / 30 / 10 | 심각도 순서를 점수로 옮긴 값. 실무 RBA도 0~100 범위의 정수 점수를 쓴다 |
| 기본 점수: 행위 탐지 | 20 | 행위 탐지는 "평소와 다름"이지 "확실히 나쁨"이 아니라 룰 medium보다 낮게 둔다 |
| 자산 중요도 계수 | high 1.5 / medium 1.0 | 1단계 `criticality`(추정). 서버가 없는 신호(웹·세션 단위)는 1.0 |
| 신뢰도 계수 | 세션 직접 소속 1.0 / 5-c 추정 연결 0.8 | 추정 연결은 확실성이 낮다 |

#### 6-2. 세션 점수 (같은 신호는 한 번만)

```
세션 점수 = Σ (세션의 탐지 종류별 최고 신호 점수)
```

- 같은 세션에서 같은 탐지 종류가 여러 번 나오면 **가장 높은 점수 1개만** 센다.
- R16은 제외한다 (6-5에서 따로 다룸).
- 세션마다 점수, 점수 구성, 신호 종류 수, **ATT&CK 전술 수**를 남긴다.

#### 6-3. ATT&CK 전술 수

5단계 기법(T번호)을 MITRE ATT&CK의 **전술**(공격 단계)로 옮긴다. 여러 단계에 걸친 활동은 단순 이상보다 실제 공격일 가능성이 높기 때문이다.

| 전술 | 해당 기법 |
|---|---|
| 초기 접근 (Initial Access) | T1078, T1133, T1190, T1078.004 |
| 실행 (Execution) | T1059, T1059.004 |
| 지속 (Persistence) | T1505.003, T1098 |
| 방어 회피 (Defense Evasion) | T1562.001, T1564.001 |
| 자격 증명 접근 (Credential Access) | T1110 |
| 탐색 (Discovery) | T1046 |
| 측면 이동 (Lateral Movement) | T1021.004 |
| 수집 (Collection) | T1560.001 |
| 명령·제어 (Command and Control) | T1071, T1105, T1571 |
| 유출 (Exfiltration) | T1567, T1048 |
| 영향 (Impact) | T1531 |
| 정찰 (Reconnaissance) | T1595 |

- 기법 하나가 여러 전술에 속하는 경우(예: T1078)는 대표 전술 하나로 정한다.
- 행위 탐지는 전술이 없어서 전술 수에 넣지 않는다.

#### 6-4. 경보 기준 (실행 전 고정)

| 기준 | 값 | 근거 |
|---|---|---|
| 점수 기준 | 세션 점수 ≥ 100 | 실무 RBA 도구(Splunk ES 등)의 기본 위험 경보가 "대상의 누적 점수 100 초과" 형태다. high 룰 하나(최대 90)만으로는 넘지 않고, 신호가 겹쳐야 넘는다 |
| 전술 기준 | ATT&CK 전술 ≥ 3 | 실무 RBA의 "여러 전술에 걸친 활동" 경보 방식을 따른다 |

둘 중 하나라도 넘으면 **경보**다. 경보 세션마다 어느 기준으로 걸렸는지 남긴다.

#### 6-5. 사람·서버 단위 누적 + 설정 위험

| 대상 | 내용 |
|---|---|
| 사람 (`person_candidate`) | 24시간·7일 창으로 세션 점수 합계. 여러 세션에 나뉜 약한 신호가 쌓이는지 확인 |
| 서버 (`host`) | 서버에서 일어난 신호 점수 합계 (같은 서버·같은 탐지 종류는 한 번). 어느 서버가 가장 많이 공격받았는지 확인 |
| 설정 위험 | R16을 계정별로 묶어 "발생 횟수, 처음·마지막"으로 보고 |
| 외부 IP | 4단계 `external_profile`을 그대로 연결 (로그인 성공 없음 → 점수 없음, 목록만) |

#### 6-6. 민감도 확인 (가중치가 임의값이라서)

| 바꿔 볼 것 | 값 |
|---|---|
| 룰 high / medium / low | 40·20·5 / 60·30·10 (기본) / 80·40·20 |
| 행위 탐지 | 10 / 20 (기본) / 30 |
| 추정 연결 신뢰도 | 0.5 / 0.8 (기본) / 1.0 |

27개 조합마다 상위 10개 세션과 경보 세션이 얼마나 바뀌는지 출력한다.

#### 6-7. 검증

- 모든 세션 점수 = 점수 구성 항목의 합
- 같은 세션·같은 탐지 종류가 두 번 더해지지 않음
- 76건의 탐지 신호가 모두 세션 점수, 서버 점수, 설정 위험 중 하나 이상에 반영됨

### 5. 민감도 확인 (`sensitivity.csv`)

가중치가 임의값이라서, 바꿔도 결과가 유지되는지 27개 조합으로 확인했다.

| 바꾼 것 | 값 |
|---|---|
| 룰 high / medium / low | 40·20·5 / **60·30·10** / 80·40·20 |
| 행위 탐지 | 10 / **20** / 30 |
| 추정 연결 신뢰도 | 0.5 / **0.8** / 1.0 |

| 결과 | 27개 조합 중 |
|---|---|
| 경보 세션이 기본(4개)과 같음 | **27** |
| 상위 4개가 같음 (S122, S132, S137, S142) | **27** |
| 상위 10개가 기본과 모두 같음 | **27** |

- 가장 약한 조합(룰 40·20·5, 행위 10, 연결 0.5)에서도 경보 4개가 유지됐다. 네 세션 모두 **전술 기준(3개 이상)** 으로도 걸리기 때문이다.
- 가장 강한 조합(룰 80·40·20, 행위 30, 연결 1.0)에서도 정상 세션은 30점(행위 1개)이라 경보가 되지 않았다.
- 즉 이 데이터에서는 **가중치의 정확한 값보다 "신호가 여러 개, 여러 전술에 걸쳐 겹치는가"가 결과를 결정**했다.

### 6. 한계

#### ① 결과가 이렇게 깔끔한 건 데이터 덕분이기도 하다

- 공격 세션은 신호가 8~12개, 정상 세션은 0~1개라 차이가 극단적이다. 합성 데이터의 특성이다.
- 실제 환경에서는 정상 세션도 신호가 2~3개씩 쌓이는 경우가 흔하고, 그때는 가중치와 기준값이 결과를 크게 바꾼다. 민감도 확인 결과가 "가중치와 상관없이 안정적"이었다고 일반화하면 안 된다.

#### ② 시나리오를 아는 상태에서 만든 탐지 위에 점수를 쌓았다

- 점수 가중치는 실행 전에 고정했지만, 그 입력인 5단계 탐지 룰은 시나리오를 아는 상태에서 골랐다 ([5단계 한계](06_탐지_위험점수.md#source-2) 7절).
- 그래서 "경보 4개 = 시나리오 4개"라는 결과는 **탐색적 결과**로 보고한다.

#### ③ 그 외

| 항목 | 내용 |
|---|---|
| 가중치 근거 | 기본 점수 60·30·10·20, 계수 1.5·0.8은 순서를 점수로 옮긴 임의값이다. 실무 RBA 도구의 범위를 참고했지만 표준값은 아니다 |
| 경보 기준 | 100점, 전술 3개는 실무 RBA 도구의 기본 경보 방식을 참고했다 |
| 자산 중요도 | 1단계 추정값이다. 기업이 실제 중요도를 주면 바뀐다 |
| 행위 탐지의 전술 | 행위 탐지는 전술에 넣지 않았다. B02·B04(T1078), B07(T1110)처럼 관련 기법이 있는 행위 탐지도 전술 수에는 포함되지 않는다 |
| 전술 매핑 | T1078처럼 여러 전술에 속하는 기법은 대표 전술 하나로 정했다 |
