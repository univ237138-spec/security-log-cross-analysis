### 1. 3단계는 어떤 작업인가

2단계에서는 이벤트를 **"누구의 것인지"** 와 **"어느 바구니인지"** 로 나눴다. 하지만 ① 사용자 업무 세션 바구니(4,885건)는 아직 **사람별로 쌓인 이벤트 더미**다. dev01의 이벤트가 16일치 섞여 있어서, 어디서부터 어디까지가 "한 번의 업무"인지 구분되지 않는다.

3단계는 이 더미를 **"출근해서 퇴근하기까지" 같은 한 덩어리씩 잘라 번호를 붙이는 작업**이다.

```
2단계 후:  dev01 이벤트 ▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪  (16일치, 경계 없음)

3단계 후:  dev01 세션 S001 ▪▪▪▪▪   S017 ▪▪▪▪   S042 ▪▪▪▪▪▪   ...
              (10/1 09:47~10:05)  (10/2 …)     (10/3 …)
```

산출물은 두 개다.

- **타임라인에 `session_id` 컬럼 추가:** 각 이벤트가 몇 번 세션에 속하는지 표시
- **세션 테이블:** 세션 1개 = 1행. 언제 시작해 얼마나 걸렸는지, 웹·서버 경로를 썼는지, 민감 행위가 몇 번 있었는지 같은 요약

4단계(기준선)와 5단계(탐지)는 이 **세션 테이블 한 행 한 행을 비교 대상**으로 쓴다. "dev01의 평소 세션은 이런데 이 세션은 다르다"고 판단하려면 세션 단위가 먼저 있어야 한다.

| 항목 | 내용 |
|---|---|
| 입력 | `data/06_classified/timeline_classified.csv` |
| 출력 | `data/07_sessions/timeline_sessions.csv` (타임라인 + `session_id`), `data/07_sessions/sessions.csv` (세션 테이블) |
| 코드 | `scripts/07_sessionize.py` |
| 결과 문서 | `docs/10_세션화/01_세션화_설명.md` |

### 3. 주의할 점

1. **웹과 ssh는 이름이 아니라 "접속 IP + 시간"으로 묶는다.** 멘토 기준(콘솔 계정과 리눅스 계정을 이름으로 조인 금지)을 지키기 위해서다. 두 로그 모두에 기록된 접속 IP를 키로 쓴다.
2. **세션 경계 기준은 데이터 분포로 정하고, 시나리오에 맞추지 않는다.** 예를 들어 웹 전용 세션의 무활동 기준은 정상 세션의 요청 간격 분포를 보고 정한다.
3. **nginx와 감사로그의 중복을 합산하지 않는다.** 같은 요청이 두 로그에 모두 남으니 세션 요약에서 로그별 건수를 따로 센다.
4. **세션 테이블에는 사실만 적고 판단은 하지 않는다.** "새벽 시작", "외부 IP" 같은 속성은 기록하되, 그게 이상인지는 4단계 기준선에서 판단한다.
5. **② 배경 활동과 ③ 외부 시도에는 세션을 만들지 않는다.** `session_id`를 비워 둔다.

### 4. 세부 계획

#### 3-1. 서버 경로 세션 만들기 (ssh 기준)

- sshd 접속(`connection_id`) 150개를 출발점으로 삼는다. 시작과 끝이 명확하기 때문이다.
- **같은 리눅스 계정 + 같은 접속 IP의 접속이 시간상 겹치면 하나의 세션으로 합친다.** (5건 해당)
- 세션 시작 = 첫 `auth_success`, 끝 = 마지막 `session_removed`

#### 3-2. 웹 이벤트 붙이기 (접속 IP + 시간)

- nginx·감사로그 이벤트의 `client_ip`가 세션의 접속 IP와 같고, 시각이 세션 시작~끝 안에 있으면 그 세션에 붙인다.
- 근거는 **관측**이다. 두 로그 모두에 접속 IP가 직접 기록돼 있다.

#### 3-3. Sysmon 사람 계정 이벤트 붙이기 (리눅스 계정 + 시간)

- Sysmon 이벤트의 계정이 세션의 리눅스 계정과 같고, 시각이 세션 안에 있으면 붙인다. 같은 리눅스 계정 체계라서 멘토 기준에 걸리지 않는다.
- `process_terminate`는 같은 `ProcessGuid`의 생성 이벤트와 같은 세션으로 둔다. 프로세스가 세션 종료 뒤에 끝나도 같은 세션이다.

#### 3-4. sshd 실패 시도 3건 붙이기

- 로그인 성공 직전의 실패 시도(dev02, 203.0.113.44)는 같은 IP·계정의 **바로 다음 세션**에 붙인다(5분 이내).

#### 3-5. 웹 전용 세션 만들기

- 3-2에서 남은 웹 이벤트(35건)는 `client_ip`별로 시간순 정렬해 **무활동 30분 이상이면 새 세션**으로 끊는다.
- 30분 근거: 정상 세션 내 웹 요청 최대 간격이 약 12.6분이다. 30분은 웹 서비스에서 흔히 쓰는 세션 만료 기준이기도 하다.
- 예상: 외부 IP 세션 1개 + 내부 IP의 짧은 웹 조각 몇 개

#### 3-6. 세션 테이블 만들기 (세션 1개 = 1행)

| 분류 | 컬럼 |
|---|---|
| 식별 | `session_id`, `session_type` (`server+web` / `server_only` / `web_only`) |
| 누구 | `person_candidate`(추정), `linux_account`, `console_accounts`, `client_ip`, `client_zone` |
| 언제 | `start_utc`, `end_utc`, `start_hour_kst`, `weekday`, `duration_min` |
| 서버 경로 | `ssh_connections`, `auth_method`, `failed_before_login`, `hosts`(Sysmon 작업 서버), `process_count`, `external_connections`(외부 목적지 연결 수) |
| 웹 경로 | `web_login_count`, `web_login_type`(일반/새 기기/root 무MFA), `nginx_count`, `audit_count`, `api_count`, `non_get_count` |
| 행위 | `sensitive_actions`(민감도 high 행위 수와 목록) |

#### 3-7. 검증

- ① 바구니 4,885건이 모두 `session_id`를 가짐, ②③은 모두 비어 있음
- 원래 컬럼 값 변화 없음
- 세션 테이블 건수 합계 = 타임라인의 세션별 건수 합계
- 세션끼리 같은 사람의 시간이 겹치지 않음 (겹치면 합쳐졌어야 함)

#### 3-8. 문서

`docs/10_세션화/`에 계획(00, 이 문서)과 결과(01) 문서를 둔다.

### 1. 결과 요약

① 사용자 업무 세션 바구니의 이벤트 4,885건을 **업무 세션 146개**로 묶었다.

| 세션 종류 | 수 | 뜻 |
|---|---|---|
| `server+web` | 143 | ssh 접속과 웹 활동이 함께 있는 세션 |
| `server_only` | 2 | ssh 접속만 있고 웹 활동이 없는 세션 |
| `web_only` | 1 | 웹 활동만 있고 ssh 접속이 없는 세션 |
| **합계** | **146** | 서버 세션 145개(ssh 접속 150개 중 겹친 5쌍을 합침) + 웹 전용 1개 |

#### 이벤트가 세션에 붙은 방법 (`work_session_link`)

| 방법 | 건수 | 근거 |
|---|---|---|
| 접속 IP + 시간 (웹 → 서버 세션 안) | 2,644 | 관측 (두 로그 모두 접속 IP 기록) |
| ssh 접속 (sshd 접속 줄) | 1,200 | 2단계 `connection_id` |
| 리눅스 계정 + 시간 (Sysmon → 서버 세션) | 553 | 같은 리눅스 계정 체계 |
| ProcessGuid (Sysmon 프로세스 종료) | 450 | 관측 (같은 프로세스) |
| 웹 전용 (접속 IP + 무활동 30분) | 19 | 규칙 5 |
| 접속 IP + ssh 종료 뒤 무활동 30분 이내 | 16 | 규칙 2 (고친 부분) |
| 로그인 직전 실패 시도 | 3 | 규칙 4 |

#### 새 컬럼 이름에 대해

- 새 세션 번호 컬럼은 `work_session_id`(업무 세션 ID)다.
- 처음에는 `session_id`로 만들었는데, sshd의 원래 컬럼 `session_id`(systemd-logind 세션 번호)와 이름이 겹쳐 원래 값을 덮어썼다. 검증(원래 컬럼 값 비교)에서 잡혀 이름을 바꿨다.

### 2. 규칙과 근거 (데이터 분포)

모든 규칙은 **정상 세션 전체의 분포**를 보고 정했다. 아래 숫자는 스크립트가 실행할 때 출력하는 '규칙 근거'와 같다.

#### 규칙 1. 서버 세션 = ssh 접속, 겹치면 합친다

| 근거 | 값 |
|---|---|
| ssh 접속 길이 | 최소 3.1분 / 중앙값 22.4분 / 최대 40.0분 |
| 같은 계정·같은 IP 접속이 시간상 겹침 | **5쌍** (ops01 4쌍, intern01 1쌍). 겹친 시간 7.3~23.2분 |
| 겹치지 않는 연속 접속 사이 간격 | 최소 0.4분 / 중앙값 1,243분(약 21시간) |

- 겹친 접속은 같은 사람이 터미널을 하나 더 연 것으로 보고 합쳤다.
- 합치는 기준은 **"겹칠 때만"(간격 0)** 이다. 겹치지 않는 접속 사이 간격은 대부분 하루 단위라 별도 세션으로 보는 게 자연스럽다. 최소 0.4분처럼 가까운 경우도 있지만, 합치는 기준을 넓히면 근거가 약해지므로 넓히지 않았다.

#### 규칙 2. 웹 이벤트 → 같은 접속 IP의 서버 세션에 붙인다

1. 시각이 **ssh 세션 시간 안**이면 붙인다.
2. ssh 종료 뒤라도 같은 IP의 웹 이벤트가 **무활동 30분 안**에 이어지면 붙이고, 세션 끝을 그 웹 이벤트까지 늘린다.
   - 세션 끝 = **서버·웹 경로가 모두 멈춘 때**

| 근거 | 값 |
|---|---|
| 웹 이벤트 중 같은 IP 서버 세션 시간 안 | 2,644 / 2,679 (**98.7%**) |
| 서버 세션 시작 → 첫 웹 이벤트 | 중앙값 2.0초 / 최대 2.0초 |
| ssh 종료 뒤 무활동 30분 안에 이어진 같은 IP 웹 이벤트 | **16건**, 세션 4개, ssh 종료로부터 3~158초 |

- 접속 IP는 두 로그 모두에 직접 기록돼 있다. 이름으로 조인하지 않는다는 멘토 기준을 지킨다.
- 30분은 규칙 5와 같은 무활동 기준이다. 웹 활동의 끝을 판단하는 기준을 하나로 통일했다.
- 세션 테이블에는 원래 ssh 종료 시각(`ssh_end_utc`)과 ssh 종료 뒤 웹 이벤트 수(`web_after_ssh_count`)를 따로 남겼다.

#### 규칙 3. Sysmon 사람 계정 이벤트 → 같은 리눅스 계정의 서버 세션 안이면 붙인다

| 근거 | 값 |
|---|---|
| 사람 계정 Sysmon 이벤트(종료 제외)가 같은 계정 서버 세션 안 | 553 / 553 (100%) |
| `process_terminate` 중 ProcessGuid로 연결 | 450 / 450 (100%) |

- sshd와 Sysmon은 둘 다 **리눅스 계정**이라 같은 계정 체계다. 멘토 기준(콘솔 계정과 리눅스 계정 이름 조인 금지)에 해당하지 않는다.
- 이 규칙은 **ssh 시간(`ssh_end_utc`까지)만** 본다. 규칙 2로 늘어난 웹 활동 구간에는 Sysmon 이벤트를 붙이지 않는다.
- 겹친 접속을 합친 뒤에는 이벤트 하나가 두 세션에 걸리는 경우가 없다 (스크립트가 확인).

#### 규칙 4. 로그인 직전 실패 시도 → 같은 IP·계정의 다음 세션 (5분 이내)

| 근거 | 값 |
|---|---|
| 해당 실패 시도 | 3건 |
| 실패 → 다음 로그인 간격 | 31초, 36초, 40초 |

- 5분은 이 3건을 여유 있게 포함하면서, 하루 단위로 떨어진 다른 접속과는 섞이지 않는 값이다.

#### 규칙 5. 남은 웹 이벤트 → 접속 IP별, 무활동 30분이면 끊는다

| 근거 | 값 |
|---|---|
| ssh 세션 안 웹 이벤트 사이 간격 | 중앙값 20초 / 99% 40초 / 최대 757초(12.6분) |

- 정상 세션에서 웹 요청이 12.6분 넘게 끊긴 적이 없다. 30분은 그보다 넉넉하고, 웹 서비스에서 흔히 쓰는 세션 만료 기준이다.

#### 처음 계획대로 실행했을 때

규칙 2가 "ssh 세션 시간 **안**"의 웹 이벤트만 붙였다. 그 결과 세션은 150개였고, 내부 IP의 **웹 전용 세션 4개**가 생겼다.

| 처음 세션 | 접속 IP | 사람 후보 | 웹 이벤트 | 직전 같은 IP 서버 세션 | ssh 종료 → 웹 시작 |
|---|---|---|---|---|---|
| S039 | 10.20.10.61 | intern01 | nginx 3 | 10-06 01:28~01:31 | 9초 |

| S053 | 10.20.10.12 | dev02 | nginx 8 | 10-06 08:02~08:08 | 18초 |
| S075 | 10.20.10.61 | intern01 | nginx 1 | 10-08 06:13~06:18 | 12초 |

- 네 세션 모두 **같은 IP의 ssh 세션이 끝나고 3~18초 뒤에 시작**했고, 웹 로그인 없이 nginx 요청만 있었다.

- 그대로 두면 4단계에서 "웹 로그인 없는 웹 전용 세션"이라는 **이상 신호로 잘못 잡힐 수 있었다 (오탐 후보).**

#### 고친 내용

- 규칙 2에 "ssh 종료 뒤 **무활동 30분 안**에 이어지는 같은 IP의 웹 이벤트도 그 세션에 붙인다"를 추가했다 (사용자 확인 후 적용).
- 근거는 규칙 5와 같은 무활동 기준(30분)이다. 특정 IP·계정·시각을 조건으로 쓰지 않았다.

### 5. 한계

#### ① 시나리오를 알고 있는 상태에서 규칙을 만들었다

- 분석자(사람과 AI 모두)는 이미 시나리오 A~D를 알고 있는 상태에서 세션 규칙을 정했다. 그래서 **무의식적으로 시나리오가 잘 드러나는 쪽으로 규칙을 고를 위험**이 있다.
- 이를 줄이려고 모든 규칙을 **정상 세션 전체의 분포**(접속 길이, 겹침, 웹 요청 간격, 실패→로그인 간격)로 정하고 2절에 숫자를 남겼다. 어떤 규칙도 특정 IP·계정·시각을 조건으로 쓰지 않는다.
- 4절의 규칙 수정도 같은 위험이 있다. 결과를 보고 규칙을 바꿨기 때문이다. 다만 이 수정은 **정상 사용자의 세션이 잘리는 문제**를 고친 것이고, 시나리오 세션의 모양은 바꾸지 않았다.
- 그래도 완전히 독립적인 검증은 아니다. 4단계 이후의 탐지 평가는 **탐색적 평가**로 보고해야 한다. 확증적 평가에는 시나리오를 모르는 상태에서 만든 규칙이나 별도 데이터가 필요하다. ([07_분석기획 5절 7번](01_프로젝트_개요.md)과 같은 입장)

#### ② 시스템 계정 활동은 세션에 붙지 않았다

- root·www-data의 활동은 2단계에서 ② 시스템 배경 활동으로 분류됐다. 그래서 이 단계에서 세션에 붙지 않았다.
- 예: S137(ops02)은 `server_only` 세션으로 잡혔지만, 같은 시간 node-01에서 root가 실행한 활동은 이 세션에 포함되지 않았다. 세션 테이블의 `process_count`, `external_connections`에도 반영되지 않는다.
- 이 연결은 4·5단계에서 "평소와 다른 시스템 활동"을 찾은 뒤 시간·서버로 붙인다.

#### ③ 그 외

| 항목 | 내용 |
|---|---|
| 겹친 접속 합치기 | "같은 사람이 터미널을 두 개 열었다"는 해석은 추정이다 |
| ssh 종료 뒤 웹 이어 붙이기 | "브라우저가 계속 열려 있었다"는 해석은 추정이다 |
| sshd 연결 중 일부 | 2단계에서 시간 근접으로 묶은 450줄(`session_new`, 로그아웃 줄)의 추정이 그대로 이어진다 |
| nginx·감사로그 중복 | 같은 요청이 두 로그에 남는다. 세션 테이블은 `nginx_count`와 `audit_count`를 따로 센다. 합쳐서 요청 수로 쓰면 안 된다 |
| 시간대 | `start_hour_kst`, `weekday_kst`는 UTC+9로 계산했다 |

### 1. 4단계는 어떤 작업인가

3단계에서 세션 146개를 만들었다. 하지만 세션 하나만 보고는 이상한지 알 수 없다. 예를 들어 ops02의 S137 세션이 "KST 02시 시작, 웹 없음"이라는 사실만으로는 판단할 수 없고, **ops02가 평소 어떻게 일하는지와 비교**해야 이상하다고 말할 수 있다.

4단계는 이 **"평소 모습"을 데이터로 만드는 작업**이다.

```
3단계 결과:  S137 = { ops02, 02시 시작, 웹 없음, 40분 }        ← 사실

4단계 기준선: ops02의 평소 = { 09~16시 시작, 항상 웹 함께 사용, 중앙값 29분 }

4단계 비교값: S137 → 시작 시각 평소 범위 밖 / 웹 없는 세션 처음 / 길이 평소 범위 안
```

| 4단계에서 하는 것 | 4단계에서 하지 않는 것 |
|---|---|
| 평소 모습(기준선)을 만든다 | "이상이다"라고 판정하지 않는다 |
| 각 세션·이벤트가 평소와 **얼마나 다른지** 비교값을 계산한다 | 임계값을 정하지 않는다 |
| | 위험점수를 매기지 않는다 |

판정은 5단계(탐지), 점수는 6단계에서 한다. 4단계는 판단 재료를 만드는 단계다.

| 항목 | 내용 |
|---|---|
| 입력 | `data/07_sessions/sessions.csv`, `timeline_sessions.csv`, `data/05_enriched/` |
| 출력 | `data/08_baseline/` 아래 `session_baseline.csv`, `background_patterns.csv`, `background_baseline.csv`, `external_profile.csv` |
| 코드 | `scripts/08_baseline.py` |
| 결과 문서 | `docs/11_기준선/01_기준선_설명.md` |

### 3. 주의할 점

1. **기준선이 공격으로 오염되지 않게 한다.** 전체 16일 데이터로 평소 모습을 만들면 공격 행동도 "평소"에 섞인다. 그래서 **각 세션은 그보다 앞선 과거만 보고 비교**한다(확장 윈도우). 실무 UEBA도 과거 데이터로 학습하고 새로 들어오는 행동과 비교한다.
2. **표본이 작다는 걸 숨기지 않는다.** 과거 세션이 적으면 개인 기준선을 믿기 어렵다. 과거가 부족하면 같은 서버를 쓰는 동료 그룹, 그것도 부족하면 전체 기준선을 쓰고, **어느 수준의 기준선을 썼는지 컬럼으로 남긴다.**
3. **비교 항목을 시나리오에 맞춰 고르지 않는다.** 비교 항목은 UEBA의 일반 범주(시간, 접속 위치, 대상 서버, 행위, 양)에서 정한다. "XMR"이나 "4444" 같은 특정 값은 쓰지 않는다. 그런 지식 기반 판단은 5-a단계(룰 탐지)의 일이다.
4. **판정하지 않고 비교값만 남긴다.** "평소 범위 밖", "처음 봄", "백분위 98%" 같은 측정값까지만 계산한다.
5. **합성 데이터라 너무 깔끔하게 나올 수 있다.** 정상 행동이 매우 규칙적이어서 차이가 뚜렷하게 보일 것이다. 실제 환경에서도 그럴 거라고 과장하지 않는다.

### 4. 세부 계획

#### 4-1. 비교 방식: "과거만 보고 비교" (확장 윈도우)

```
10/1 ─── 10/5 ─── 10/10 ─── 10/15 S137
 └──── 이 구간의 ops02 세션만 사용 ────┘   → S137과 비교
```

- 각 세션의 기준선 = **그 세션 시작 전에 끝난** 같은 사람의 세션들
- 미래 데이터를 쓰지 않으므로 공격이 자기 자신이나 이전 세션의 기준선에 섞이지 않는다.
- 앞쪽 세션은 과거가 적으니 4-2의 단계별 대체 기준선을 쓴다.

#### 4-2. 기준선 수준 (표본 크기에 따라)

| 수준 | 조건 | 내용 |
|---|---|---|
| `person` | 같은 사람의 과거 세션 ≥ 5개 | 개인 기준선 |
| `peer` | 개인 과거가 5개 미만, 같은 주 작업 서버 동료의 과거 세션 ≥ 5개 | 동료 그룹 (예: app-01 = dev01, dev02, intern01). 그룹은 보강 테이블의 `home_host`(추정) 기준 |
| `global` | 위 둘 다 부족 | 전체 사용자 과거 세션 |
| `none` | 전체 과거도 5개 미만 | 비교하지 않음 (첫날 초반) |

- 5개 근거: 백분위나 "본 적 있음"을 말하려면 최소한의 반복이 필요하다. 사람별 세션 수(12~29)의 앞쪽 일부만 대체 기준선을 쓰게 되는 값이다.
- 세션마다 `baseline_level`, `baseline_n`(비교에 쓴 과거 세션 수)을 남긴다.

#### 4-3. 세션 비교 항목 (UEBA 일반 범주)

| 범주 | 항목 | 비교 방식 | 남기는 비교값 |
|---|---|---|---|
| 시간 | 시작 시각(KST) | 과거 시작 시각 분포 | 과거 최소~최대 범위 밖인가, 평소에서 몇 시간 벗어났나 |
| | 요일 | 과거 주말 세션 비율 | 주말인가, 과거에 주말 세션이 있었나 |
| 접속 위치 | 접속 IP | 과거 IP 목록 | 처음 보는 IP인가, 외부 IP인가 |
| 경로 | 세션 종류 | 과거 `session_type` 비율 | 이 종류의 과거 비율 (예: server_only 0%) |
| | 웹 로그인 종류 | 과거 로그인 종류 | 처음 보는 로그인 종류인가 |
| 인증 | ssh 인증 방식, 로그인 전 실패 | 과거 값 | 처음 보는 방식인가, 과거에 실패가 있었나 |
| 대상 | 작업 서버 | 과거 서버 목록 | 처음 가는 서버인가 |
| 행위 | 실행 명령 | 과거 명령 목록 (개인, 그리고 전체 사용자) | 처음 보는 명령 수와 목록 |
| | 민감 행위 | 과거 민감 행위 목록 | 처음 하는 민감 행위인가 |
| | 외부 연결 | 과거 외부 연결 수 | 과거에 외부 연결이 있었나 |
| 양 | 길이, 프로세스 수, nginx·API 요청 수, GET 외 요청 수 | 과거 분포 | 과거 대비 백분위 |

- 명령은 숫자 부분을 정규화해 비교한다. 예: `/tmp/health-610274` → `/tmp/health-N`
- 결과는 세션 테이블에 비교값 컬럼을 붙인 `session_baseline.csv`로 만든다.

#### 4-4. ② 시스템 배경 활동의 기준선 (서버별 패턴)

시스템 활동은 세션이 없으니 **서버별 반복 패턴**을 기준선으로 쓴다.

| 이벤트 | 패턴 정의 |
|---|---|
| 프로세스 생성 | 서버 + 계정 + 실행 파일 + 명령(정규화) |
| 네트워크 연결 | 서버 + 계정 + 실행 파일 + 목적지 구역(server/external) + 목적지 포트 |
| 파일 생성 | 서버 + 계정 + 실행 파일 + 파일 경로(정규화) |

- 이벤트마다 **그 시점 이전에 같은 패턴을 몇 번 봤는지**(`pattern_seen_before`)와 다른 서버에서 본 적이 있는지를 남긴다.
- 예: `probe.py`는 처음 몇 번 이후로는 수백 번 본 패턴이 되고, 한 번만 나온 패턴은 "처음 봄"으로 남는다.
- `process_terminate`는 같은 `ProcessGuid` 생성 이벤트의 값을 따른다.
- 결과: 패턴 목록 `background_patterns.csv` + 이벤트별 비교값 `background_baseline.csv`

#### 4-5. ③ 외부 시도 프로필 (IP별 요약)

외부 시도는 비교할 "평소"가 없으므로 **IP별 요약**만 만든다.

- 처음·마지막 시도 시각, 시도 횟수, 하루 평균, 시도한 계정명 수와 목록, 성공 여부
- 결과: `external_profile.csv`

#### 4-6. 검증

- 모든 세션의 기준선에 **그 세션보다 늦게 끝난 세션이 하나도 없음** (미래 데이터 누수 없음)
- 세션 146개, ② 이벤트 4,079개 모두 비교값이 있음 (`none` 수준은 명시)
- 기준선 수준별 세션 수 출력

### 5. 실행 중 보완한 것

- **양 비교값에 `_above_max` 추가:** 처음에는 백분위(`_pct`, 과거 값 중 이하인 비율)만 만들었다.
- 그런데 과거 값이 대부분 같으면 백분위가 100%로 몰렸다. 예를 들어 GET 외 요청 수는 거의 항상 0이라, 0인 세션도 "과거 100%와 같거나 큼"이 되어 **141개 중 139개가 100%** 였다.
- 그래서 "과거 최대보다 큰가"(`_above_max`)를 따로 남겼다. 보완 후 GET 외 요청 수가 과거 최대를 넘은 세션은 141개 중 2개다.

### 6. 한계

#### ① 시나리오를 알고 있는 상태에서 비교 항목을 골랐다

- 비교 항목은 UEBA 일반 범주에서 골랐고 특정 IP·명령·포트를 쓰지 않았다. 하지만 분석자가 시나리오를 아는 상태였다는 점은 3단계와 같다.
- 4단계 이후 결과는 **탐색적 평가**로 보고한다. ([3단계 한계](05_세션화_기준선.md#source-2) 5절과 같은 입장)

#### ② 표본이 작다

- 개인 기준선은 과거 세션 5~28개로 만든다. 시작 시각 범위처럼 최소·최대를 쓰는 값은 표본이 작을수록 좁아져 "범위 밖"이 자주 나온다 (2절: 정상 세션 25개가 범위 밖, 대부분 1시간).
- 앞쪽 세션 40개(none 5, global 15, peer 20)는 개인 기준선 없이 비교했다. 이 세션들의 "처음 봄"은 과거 부족 때문일 수 있다.

#### ③ 합성 데이터라 너무 깔끔하다

- 정상 명령 5종, healthcheck 패턴처럼 정상 행동이 매우 규칙적이다. 그래서 처음 보는 명령·패턴이 뚜렷하게 구분된다.
- 실제 운영 환경에서는 정상 행동도 훨씬 다양해서, 같은 방식으로 이렇게 깔끔한 구분이 나온다고 기대하면 안 된다.
