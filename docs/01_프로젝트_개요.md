# 프로젝트 개요

[문서 목록](README.md) · [데이터 목록](../data/README.md)

협력 기업 테이렌이 Snowflake `security_logs.raw`로 제공한 보안 로그 4종을 교차 분석한다. 서로 다른 형식과 계정 체계를 정리하고, 업무 세션과 시스템 활동의 맥락을 붙여 조사할 경보를 찾는 데이터 분석 프로젝트다.

| 로그 | 기록하는 내용 | 원문 형식 |
|---|---|---|
| sshd | SSH 로그인·인증 실패·접속 종료 | syslog 텍스트 |
| nginx | 웹 요청 경로·응답 코드 | combined 텍스트 |
| sysmon | 프로세스·네트워크·파일 이벤트 | XML |
| audit | 보안 솔루션 콘솔의 계정·설정·사용자 행위 | JSON |

데이터의 이벤트 기간은 2026-09-30~2026-10-16 UTC다. 이벤트 시각이 적재 시각보다 늦은 사례 등으로 합성 데이터일 가능성이 있으나 제공 기업의 확정 설명으로 취급하지 않는다. 실제 운영 환경에 대한 성능으로 일반화하지 않는다.

## 분석 질문

1. 로그의 원문 정보를 유지하면서 공통 시간·행위 구조로 바꿀 수 있는가?
2. 서로 다른 로그의 계정·접속·프로세스를 어떤 근거로 연결할 수 있는가?
3. 정상 세션의 분포와 알려진 행위 규칙을 함께 사용해 조사 우선순위를 정할 수 있는가?
4. 경보에서 관측된 사실과 사용자 귀속 추정, 추가로 필요한 로그를 구분할 수 있는가?

## 설계 원칙

- UTC로 시각을 통일하고 원문은 `rawEvent`, 사용하지 않는 원본 필드는 `unmapped`에 보존한다.
- 리눅스 계정과 콘솔 계정은 서로 다른 체계다. 이름만으로 조인하지 않는다.
- Sysmon `src`는 서버 자신의 IP다. 통합 단계에서 `dvc`로 옮긴다.
- 동일인 후보·서버 역할에는 관측 또는 추정 근거를 붙인다.
- 기준선은 각 세션보다 과거의 완료 세션으로 구성한다.
- 탐지 신호, 위험점수·경보, 조사 판정을 별도 단계로 만든다.

## 분석 결과의 해석

현재 스냅샷에는 통합 이벤트 9,125개, 업무 세션 146개, 탐지 신호 76개, 경보 세션 4개가 있다. 경보는 조사 우선순위이며 공격 성공이나 유출 성공의 확정 판정이 아니다. 통계 검정은 탐색적이며 독립된 정답 라벨 기반 탐지 성능 평가를 수행한 것으로 해석하지 않는다.

통계 코드의 시나리오 A~D 계정·시각은 기존 분석기획에서 지정한 참고 표본이다. 시나리오 지식을 이용한 사후 평가에는 편향 가능성이 있다. 구체적인 표본과 한계는 [통계 검정](08_통계검정.md)에 남긴다.
